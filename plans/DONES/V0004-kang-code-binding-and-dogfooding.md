## 왜 이 플랜인가

v1 은 문서와 문서 사이의 참조를 강제한다. 이 플랜은 그 참조를 코드까지 넓힌다. 그리고 kang 을 kang 자신에게 적용한다.

세 목표가 서로를 검증한다.

| 목표 | 무엇을 증명하는가 |
|---|---|
| (a) 저장소 문서를 `.kang` 으로 옮김 | kang 이 실제 문서 모음에서도 동작한다. 지금 있는 성능 수치와 한계 수치는 모두 테스트용으로 만든 픽스처에서 측정한 값이다 |
| (b) kang 자신의 Rust 코드에 매크로 | 코드와 문서의 연결이 컴파일 시점에 동작한다. 첫 사용자는 kang 자신의 저장소다 |
| (c) TypeScript 구현체 + 문서 충실도 테스트 | kang 을 실제로 쓸 프로젝트(Rust 툴체인이 없는 프로젝트)에서도 동작한다 |

## 착수 전 결정 — 해소됨 (2026-08-06)

세 충돌을 사용자 결정과 저장소의 이전 사례로 해결했다. 다시 논의하지 않는다.

### B1. 의존성 — V0001 §10.1 에 크레이트별 목록을 두었다 (해소)

**컨트롤러가 잘못 적은 것을 바로잡는다:** `sha2` 제약은 V0001 에 있지 않았다. 그 제약은 V0002 의 「전역 제약」 절과 「What already exists」 절의 표에 있었다. V0001 §10 에는 의존성 목록이 아예 없었다.

**결정(사용자):** 제약이 적용되는 범위를 새로 해석하지 않는다. 목록 자체를 고친다. V0001 에 §10.1 「의존성 목록」을 새로 만들고 크레이트별로 적었다. `kang` 은 `sha2` 를 쓰고, `kang-macros` 는 `syn`, `quote`, `proc-macro2` 를 쓴다. 목록에 없는 의존성은 쓰지 않는다. 의존성을 늘려야 하면, 그 절을 고치고 근거를 남긴다.

컨트롤러는 "제약은 컴파일러의 신뢰 경계에만 적용된다" 라는 해석을 제안했다. 이 해석은 채택하지 않았다. 결과는 같다. 그러나 이 해석을 쓰면 제약을 읽는 사람이 범위를 다시 추론해야 하고, 사람마다 추론 결과가 달라질 수 있다. 목록은 사람마다 달라지지 않는다.

**워크스페이스 분할은 선택이 아니라 Rust 의 요구다.** `proc-macro = true` 인 크레이트는 같은 크레이트 안에 바이너리나 라이브러리를 함께 둘 수 없다.

### B2. 심볼 인덱스 — `kang index` 별도 명령 + 탭 구분 텍스트 (해소)

**결정(사용자):**

```
docs/A.결제\tkeyword\ta3f9c1
docs/A#결제의 방법\ttopic\tb721e0
docs/A!무료 상품\texception\tb721e0
```

- `build` 는 파일을 읽기만 한다는 성질을 지킨다. 스펙 6.2 를 고치지 않는다.
- proc-macro 쪽 파서가 의존성 없이 3줄이다. `line.split('\t')` 이면 된다.
- 사람이 읽을 수 있고 `grep` 으로 찾을 수 있다.
- 중첩 구조는 담을 수 없다. 그러나 지금 담을 중첩 구조가 없다. 필요해지면 그때 판단한다.

**주소는 `ImportAddress::parse` 가 다시 읽을 수 있는 형태여야 한다.** 출력한 주소를 다시 읽는 테스트로 이 조건을 고정한다. 이 형식의 약점은 하나뿐이다. 심볼 이름에 탭이 들어가면 형식이 깨진다. 스펙 6.0 의 이름 금지 문자 목록에 탭을 넣을지는 Task 3 에서 결정한다.

### B3. 부트스트랩 순환 — warn + `KANG_REQUIRE_INDEX` (컨트롤러 결정)

**저장소의 이전 사례를 따른다.** Task 13 이 같은 문제를 `KANG_REQUIRE_YAML` 로 해결했다. 파서가 없으면 검사를 건너뛴다. 단, 환경 변수가 켜져 있으면 panic 한다.

- 인덱스가 없으면 warn 을 출력하고 통과한다. 그래서 부트스트랩을 할 수 있다.
- `KANG_REQUIRE_INDEX=1` 이면 컴파일 에러가 난다. CI 와 릴리즈에서 이 값을 켠다.
- 아무 출력 없이 통과하는 방식(선택지 ii)은 채택하지 않는다. 이 방식에서는 인덱스를 지우면 검증이 사라지는데도 빌드가 성공한다. 이 저장소에서 이미 열세 번 겪은 "확인해 보면 사실이 아니다" 문제가 한 번 더 생긴다.
- 부트스트랩 순서를 `xtask` 나 `Makefile` 에 고정한다. 그러면 사람이 순서를 기억하지 않아도 된다.

**최종 리뷰 우선순위 1.** 지금 워크플로는 `v*` 태그에서만 실행된다. 그래서 평소의 푸시와 PR 에서는 `cargo test` 가 한 번도 실행되지 않는다. `clippy` 와 `fmt` 는 CI 에 아예 없다. 이 플랜은 크레이트를 늘린다. 그런데 지금은 회귀를 잡을 곳이 없다.

**파일:** `.github/workflows/ci.yml` (신규)

## Task 2 — 주소 문법 완결

**최종 리뷰 우선순위 2.** 이 항목은 V0002 완료 조건에서 아직 채우지 못한 항목이다. 코드 심볼 이름에는 `crate::mod::fn` 같은 형태가 들어간다. 그래서 매크로 작업을 시작하기 전에 이 항목을 끝내야 한다.

- [x] **심볼 이름의 `/` 금지** — 스펙 6.0 「주소 분할 규칙」 의 금지 항목 2 가 이 규칙을 정했다. 그 아래 목록은 이 검사를 `K105` 와 같은 종류의 검사로 할당했다. 아직 구현하지 않았다. 세 금지 중에서 이 금지만 빌드를 막는다(`## 환불/취소` 는 컴파일을 통과한다. 그러나 그 topic 을 import 한 문서에는 어떤 명령으로도 핀을 붙일 수 없다)
  - **`K115`** 를 새로 만들었다 (`src/parse.rs`). `src` 가 실제로 출력하는 코드는 `K101`~`K114` 이다. 그래서 `K100`-`K199` 범위에서 다음 빈 번호를 썼다. `K105` 를 다시 쓰지 않은 이유가 있다. `K105` 의 문구("topic 헤딩에 백틱이 있습니다")는 keyword 와 exception 에는 맞지 않는다. 그리고 같은 목록이 `K113` 에 새 번호를 준 것과 같은 할당 규칙을 따랐다

  - fix 는 `[edit]` 이다. 줄 번호는 `action` 에 넣지 않는다 (ADR-0003)
- [x] **keyword 이름 한 조각의 `.` 금지** — 최종 리뷰는 "문제가 없으므로 스펙 문구에서 빼는 편이 맞다" 고 결론 내렸다. 금지할지, 스펙에서 뺄지 결정하고 근거를 남긴다
  - **결정: 스펙에서 뺀다. 코드는 0줄이다.** 스펙 6.0 의 금지 항목 3을 삭제했다. 삭제한 곳에 근거를 남겼다
