# V0005 Orca 용 kang 플러그인 설계

이 문서는 Orca 에서 `.kang` 문서를 읽기 쉽게 보여 주는 플러그인의 설계와 그 이유를 설명한다. 플러그인은 두 가지 일을 한다.

1. `.kang` 문서를 마크다운처럼 렌더링해서 보여 준다.
2. 문서 사이의 import 연결을 Obsidian 의 Graph view 와 같은 그래프로 보여 준다.

관련 문서는 `V0001-kang-language-design.md` 와 `V0004-kang-code-binding-and-dogfooding.md` 다. V0001 은 문법의 기준이다. V0004 는 `kang index` 가 파일을 쓰는 방식을 정했다.

각 결정 끝에는 누가 정했는지 적는다. "사용자가 정했다" 는 사용자가 직접 고른 것이다. "작성자가 정했다" 는 설계 작성자가 고른 것이고, 구현 전에 사용자가 다시 볼 수 있다.

---

## 사람이 Orca 에서 `.kang` 문서를 읽기 어렵다

Orca 는 `.kang` 파일을 원본 텍스트로 연다. 그래서 `keyword` 선언 줄, `import` 줄, frontmatter 가 기호 그대로 보인다. import 한 keyword 의 정의를 보려면 그 keyword 를 선언한 문서를 따로 열어야 한다.

kang 의 주 사용자는 LLM 에이전트다. 에이전트는 `kang show` 로 상위 정책을 펼친 YAML 을 받으므로 원본을 읽지 않는다. 이 플러그인의 사용자는 사람이다. 사람이 Orca 에서 문서를 직접 열어 읽을 때 쓴다.

## 플러그인이 하는 것과 하지 않는 것

플러그인은 다음 일을 한다.

- `.kang` 파일을 열면 렌더링 화면이 먼저 보인다. 원본 보기는 Orca 가 기본으로 주는 토글로 연다.
- 렌더링 화면에서 다른 문서의 keyword 를 참조한 곳에 마우스를 올리면 정의가 보인다. 그곳을 클릭하면 그 keyword 를 선언한 문서가 열린다.
- 그래프 화면은 저장소의 모든 문서와 import 연결을 한 번에 보여 준다. 점을 클릭하면 그 문서가 열린다.
- 문서를 고친 뒤 `kang build` 를 한 번 실행하면 그래프가 최신이 된다.

플러그인은 다음 일을 하지 않는다.

- 렌더링 화면에서 편집하지 않는다. 편집은 Orca 의 원본 보기에서 한다.
- 컴파일 진단을 보여 주지 않는다. 진단은 `kang build` 가 터미널에 출력한다.
- 그래프에서 지금 연 문서를 강조하지 않는다. Orca 가 편집기에 파일 경로를 주지 않기 때문이다.
- keyword 나 topic 을 그래프의 점으로 쓰지 않는다. 점 하나는 문서 하나다.
- Orca 플러그인 카탈로그에 공개하지 않는다. 지금은 이 저장소 폴더에서 직접 설치한다.

다음 결과가 나오면 플러그인이 동작하더라도 실패로 본다.

- 렌더링 화면이 원본과 다른 뜻을 보여 준다. 예를 들어 import 한 keyword 의 정의로 다른 문서의 정의를 보여 준다.
- 플러그인이 `.kang` 파일 내용을 바꾼다.
- 그래프가 오래된 데이터를 보여 주는데, 사용자가 그것을 알 방법이 없다.

## Orca 의 제약이 설계를 정한다

아래 제약은 Orca 1.4.253 에서 확인했다. 근거는 플러그인 작성 가이드(`orca skills get orca-plugin-authoring`)와 타입 파일 두 개다. 타입 파일은 `/Applications/Orca.app/Contents/Resources/plugins/types/` 의 `orca-frame.d.ts` 와 `orca-host.d.ts` 다.

1. custom editor 는 자기 파일 하나의 내용만 받는다. 다른 파일은 읽지 못한다.
2. custom editor 는 자기 파일의 경로를 모른다. 편집기가 받는 문서 정보에는 `version`, `readOnly`, `content` 만 있다. 패널에도 탭이 바뀌었다는 이벤트가 없다.
3. 다른 파일을 Orca 탭으로 여는 `editor.open` 은 worker 에만 있다. 이 기능에는 workspace id 가 꼭 필요하다.
4. Orca 는 지금 선택된 workspace 의 이름, branch, 터미널 목록만 준다. 경로와 workspace id 는 주지 않는다. 경로와 id 는 모든 workspace 의 목록인 `workspace.list` 에만 있다.
5. 편집기 탭은 항상 파일 하나와 연결된다. 파일이 없는 탭은 만들 수 없다.
6. 플러그인에는 네트워크가 없다. 마크다운 렌더러와 그래프 라이브러리를 플러그인 폴더 안에 넣어야 한다.
7. Orca 는 `.json` 으로 끝나는 파일을 원본 보기로 연다. `.kang.json` 처럼 확장자가 더 긴 파일은 플러그인 화면으로 바로 연다.
8. worker 를 쓰는 플러그인은 설치할 때 사용자 승인이 필요하다. worker 는 사용자 컴퓨터의 Node 로 실행된다.

이 제약 때문에 렌더링 화면 혼자서는 keyword 정의를 찾을 수 없다. 다른 문서를 읽는 일과 다른 문서를 여는 일은 모두 worker 가 한다.

## `kang build` 가 그래프 인덱스를 쓴다

`kang build` 는 성공할 때마다 `.kang/graph.kang.json` 을 다시 쓴다. 이 파일을 이 문서에서는 그래프 인덱스라고 부른다. 사용자가 정했다.

그래프 인덱스에는 목록이 세 개 있다.

- 문서 목록. 문서마다 경로, description, 문서 해시, scope 가 있다. scope 는 그 문서 본문의 참조가 가리키는 심볼 목록이다. 이름 풀이는 컴파일러가 하고, 렌더링 화면은 scope 에서 찾기만 한다.
- keyword 목록. keyword 마다 선언한 문서의 경로, 이름, 정의가 있다.
- 연결 목록. 연결마다 import 하는 문서, import 되는 문서, import 한 심볼 이름들이 있다.

문서 해시는 문서 파일 전체의 해시다. 맨 앞 BOM(U+FEFF) 하나를 떼고, `crates/kang/src/hash.rs` 의 `normalize` 로 정규화한 텍스트의 SHA-256 전체 값이다. 컴파일러가 BOM 을 떼고 문서를 읽으므로 해시도 BOM 을 뗀다. rev 핀은 BOM 을 떼지 않고 같은 정규화 뒤에 앞 6자리만 쓴다. 그래서 rev 핀 값은 바뀌지 않는다. 문서 해시는 문서를 찾는 데 쓰므로, 다른 문서와 우연히 같아지지 않게 전체 값을 쓴다. 작성자가 정했다.

`kang build` 가 컴파일 error 로 끝나면 그래프 인덱스를 쓰지 않는다. `kang index` 와 같은 규칙이다. 작성자가 정했다.

같은 문서에서는 항상 같은 바이트를 쓴다. 출력은 문서 경로로 정렬하고, 만든 시각은 넣지 않는다. 그래서 문서가 바뀌지 않으면 git 에 변경이 생기지 않는다. 이 저장소에서는 그래프 인덱스를 git 에 커밋한다. `.kang/index.tsv` 와 같은 방식이다. 작성자가 정했다.

그래프 인덱스는 `crates/kang/src/main.rs` 의 `write_output` 으로 쓴다. `kang index` 와 `kang types` 도 `generate` 를 거쳐 이 함수를 쓴다. 이 함수는 그 경로에 kang 이 만들지 않은 파일이 있으면 덮어쓰지 않는다. 작성자가 정했다.

저장소의 `.kang` 이 저장소 밖을 가리키는 링크면 `kang build` 는 그래프 인덱스를 쓰지 않는다. 종료 코드 2 와 이유를 알리는 문구로 끝난다. 커밋된 링크 하나로 남의 디렉토리에 쓰지 않기 위해서다. 작성자가 정했다.

JSON 은 라이브러리 없이 직접 쓴다. V0001 §10.1 의 의존성 목록에서 `kang` 크레이트가 쓰는 외부 의존성은 `sha2` 하나다. YAML 출력도 같은 이유로 직접 썼다.

## 그래프 화면은 문서 사이의 import 를 그린다

그래프 화면은 그래프 인덱스를 열면 보인다. 사용자가 정했다. 그래프 화면은 다음과 같이 그린다.

- 점 하나는 문서 하나다.
- 문서 A 가 문서 B 의 심볼을 import 하면 A 에서 B 로 가는 화살표를 그린다.
- 같은 두 문서 사이에 import 가 여러 개 있어도 화살표는 하나다. 화살표에 마우스를 올리면 import 한 심볼 목록이 보인다.
- 점의 크기는 그 문서를 import 하는 문서의 수로 정한다.
- 점을 클릭하면 그 문서가 렌더링 화면으로 열린다.
- 사용자는 그래프를 드래그하고, 확대하고, 축소할 수 있다.

## 렌더링 화면은 원본 기호를 감추고 정의를 보여 준다

사용자는 목업 두 개 중에서 A 안을 골랐다. A 안은 import 를 칩으로 보여 주고, keyword 참조를 링크로 보여 준다.

- frontmatter 의 description 은 문서 맨 위에 인용 블록처럼 보여 준다.
- import 줄은 문서 위쪽에 칩으로 보여 준다. 칩에는 심볼 이름과 문서 경로가 있다.
- `keyword` 선언 줄은 용어 카드로 보여 준다. 카드에는 굵은 이름과 정의가 있다.
- 본문에서 keyword 를 참조한 곳은 링크로 보여 준다. 마우스를 올리면 정의가 보이고, 클릭하면 그 keyword 를 선언한 문서가 열린다.
- topic 참조(`#topic`)도 링크로 보여 준다. 그래프 인덱스에는 topic 목록이 없으므로, 링크를 클릭하면 그 topic 이 있는 문서를 연다. 작성자가 정했다.
- `exception`, `cover`, `pending`, `uncoded`, `iknow` 줄은 원본 기호를 감추고 표시만 한다. 표시 방법은 구현하는 사람이 정한다.
- 나머지 본문은 일반 마크다운으로 렌더링한다.
- 렌더링 화면은 Orca 의 밝은 테마와 어두운 테마를 따른다.
- 렌더링 화면은 읽기 전용이다. 작성자가 정했다.

## 플러그인은 이 저장소 안에 있다

플러그인은 이 저장소 안에 둔다. 설치는 이 저장소 폴더에서 직접 한다(`orca plugin install ./orca-plugin`). 둘 다 사용자가 정했다.

플러그인 폴더는 저장소 루트의 `orca-plugin/` 이다. 플러그인 id 는 `kang` 이다. Orca 는 `orca-` 로 시작하는 id 를 예약했으므로 그 id 는 쓸 수 없다. 작성자가 정했다.

플러그인은 세 부분으로 나뉜다.

- custom editor 하나는 `.kang` 파일을 렌더링 화면으로 연다.
- custom editor 하나는 `.kang.json` 파일을 그래프 화면으로 연다.
- worker 하나는 그래프 인덱스를 읽어 두 편집기에 준다. 편집기가 요청하면 문서를 Orca 탭으로 연다.

worker 는 `kang` 바이너리를 실행하지 않고 그래프 인덱스만 읽는다. 그래서 사용자 컴퓨터의 PATH 에 `kang` 이 없어도 두 화면이 동작한다.

## worker 는 문서 해시로 지금 연 문서를 찾는다

렌더링 화면은 자기 파일의 경로를 모른다(제약 2). 그래서 렌더링 화면은 받은 텍스트를 worker 에 보낸다. worker 가 그 텍스트의 문서 해시를 계산하고, 그래프 인덱스에서 같은 문서 해시를 가진 문서를 찾는다. 작성자가 정했다.

worker 는 다음 순서로 문서를 찾는다. 사용자가 정했다.

1. worker 는 `workspace.list` 로 열린 workspace 목록을 받는다. 그리고 각 workspace 경로에서 그래프 인덱스를 읽는다.
2. worker 는 각 그래프 인덱스에서 문서 해시가 같은 문서를 찾는다.
3. 같은 문서가 여러 workspace 에 있으면, worker 는 이름과 branch 가 지금 선택된 workspace 와 같은 쪽을 고른다.
4. 그래도 하나로 정해지지 않으면, worker 는 후보들이 같은 git 저장소의 worktree 인지 확인한다. 같은 저장소이면 정의를 보여 준다. 문서 내용이 같으므로 정의도 같다. 클릭한 문서는 목록의 첫 번째 worktree 에서 연다.
5. 후보들이 서로 다른 저장소에 있으면 정의를 보여 주지 않는다.

같은 문서 해시를 찾지 못하면, 그래프 인덱스가 오래되었거나 그 문서가 다른 저장소에 있다. 이때 렌더링 화면은 keyword 정의와 링크를 보여 주지 않는다. 대신 "`kang build` 를 실행하세요" 라는 안내를 보여 준다. 이렇게 하면 틀린 정의를 보여 주지 않는다.

worker 는 정의를 보여 주기 전에, 그 keyword 를 선언한 문서 파일의 지금 문서 해시도 그래프 인덱스와 비교한다. 두 값이 다르면 그 정의를 보여 주지 않는다. 작성자가 정했다.

그래프 화면도 같은 방법으로 오래된 데이터를 알린다. worker 는 각 문서 파일의 지금 문서 해시를 그래프 인덱스의 값과 비교한다. 하나라도 다르면 그래프 위에 "인덱스가 오래되었습니다" 라는 안내를 보여 준다.

Rust 와 TypeScript 는 같은 문서에서 같은 문서 해시를 계산해야 한다. 테스트로 두 쪽의 결과를 비교한다.

원격 workspace 는 지원하지 않는다. 사용자가 정했다. worker 는 사용자 컴퓨터에서 실행되므로 SSH 같은 원격 host 의 파일을 읽지 못한다. worker 는 1번 단계에서 원격 workspace 를 뺀다. 원격 workspace 의 문서만 후보로 남으면 "원격 workspace 는 지원하지 않습니다" 라는 안내를 보여 준다.

## 구현하는 사람이 정할 것

- 마크다운 렌더러와 그래프 라이브러리. 둘 다 플러그인 폴더 안에 넣어야 한다(제약 6).
- 그래프 인덱스 JSON 의 필드 이름. 위의 세 목록은 모두 있어야 한다.
- 렌더링 화면이 `.kang` 문서를 파싱하는 방법. 문법은 V0001 을 따른다.
- 그래프 인덱스가 없을 때 보여 줄 안내 문구. "`kang build` 를 실행하세요" 와 같은 뜻이면 된다.
- 테스트 방법. Rust 쪽은 기존 테스트 방식을 따른다. 플러그인 쪽은 `orca plugin test` 와 `orca plugin check` 를 쓴다.

## 남은 위험

같은 저장소의 worktree 가 여러 개이고 이름과 branch 로도 하나를 고르지 못하면, 클릭한 문서가 사용자가 기대하지 않은 worktree 에서 열릴 수 있다. 사용자는 이 경우를 받아들였다.

내용이 똑같은 문서 두 개가 한 workspace 안에 있으면, 문서 해시로 하나를 고를 수 없다. 이때 렌더링 화면은 정의를 보여 주지 않는다.

새 `.kang` 파일을 만들고 `kang build` 를 하지 않으면, 그 문서는 그래프에 없다. 인덱스에 없는 문서이므로 stale 알림도 나오지 않는다. worker 가 이 문서를 찾으려면 kang 의 파일 탐색과 무시 규칙을 똑같이 다시 만들어야 한다. 그래서 인덱스만 읽는다.

컴파일러는 같은 줄에 따로 쓴 백틱 이름 둘을 한 이름으로 읽을 수 있다. 예를 들어 `` `주문` 의 `상태` `` 는 `주문.상태` 가 scope 에 있으면 `주문.상태` 하나다. 렌더링 화면은 `주문` 과 `상태` 두 링크로 그린다. 이것은 컴파일러의 알려진 한계이고, 화면은 원문에 쓴 점을 따른다. 점으로 이은 참조는 컴파일러와 같은 순서로 scope 의 이름으로 나눈다. 컴파일러는 한 줄의 백틱 이름을 모두 한 묶음으로 나누고, 화면은 참조 하나 안에서만 나눈다. 그래서 드물게 링크의 tooltip 이 컴파일러의 해석과 다를 수 있다. 조각이 64 개를 넘는 점 참조는 화면이 멈추지 않도록 나누지 않는다.

그래프 인덱스는 커밋되는 파일이므로 믿을 수 없는 입력이다. 그래서 worker 는 파일 하나를 32 MiB 까지만 읽고, 문서가 10 000 개를 넘는 인덱스는 없는 것으로 본다. 요청 하나가 workspace 하나에서 읽는 파일 크기의 합이 64 MiB 를 넘으면 그 workspace 를 건너뛴다. 다른 workspace 에도 맞는 문서가 없으면 화면은 "`kang build` 를 실행하세요" 를 보여 준다. 하지만 `kang build` 를 해도 이 안내는 없어지지 않는다.
