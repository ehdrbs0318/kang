# V0001 — kang 언어 설계

문서 전용 언어 `kang`의 언어 명세와 CLI 계약을 정의한다.

---

## 1. 배경

정책 문서를 마크다운으로 관리하면서 두 가지 문제가 발생했다.

1. **SoT 분열** — 한 개념에 대한 "정답"이 여러 문서에 흩어져 서로 다른 내용을 말한다. 문서 A를 작성하는 LLM 에이전트가 관련 문서 B를 참조하지 못한 채 새 문서를 쓰기 때문이다.
2. **코드-문서 불일치** — 문서를 쓰는 에이전트와 코드를 쓰는 에이전트가 달라서, 한쪽이 바뀌어도 다른 쪽이 따라가지 못한다.

핵심 진단: 문제는 **문서의 크기**가 아니라 **한 개념에 대한 정답의 종류**가 늘어나는 것이다. 크기는 감내할 비용이고, 종류의 증식이 해결 대상이다.

## 2. 설계 원칙

- **개념의 주인은 하나** — 하나의 키워드는 정확히 한 파일이 정의한다. 중복은 컴파일 에러다.
- **참조는 명시적** — 다른 문서의 개념을 쓰려면 반드시 `import` 해야 한다. 미선언 참조는 에러다.
- **LLM은 원본을 보지 않는다** — CLI가 출력한 결과만 참조한다. 컴파일에 실패한 문서는 출력되지 않는다.
- **최신 버전만 존재한다** — override 문법이 없다. 정책을 바꾸려면 owner 파일을 직접 고쳐야 한다.
- **판단은 선언으로 고정한다** — 사람이나 LLM의 판단이 필요한 지점마다 선언 문법을 둔다. 판단은 1회로 끝나고, 이후의 검사는 전부 기계적이다.
- **의도적 마찰** — 개념이 중복되거나 예외가 방치되면 사용자를 귀찮게 만든다. 귀찮음이 SoT 분열을 막는다.
- **LLM에게 덜 읽을 선택권을 주지 않는다** — 출력 분량 표시, 깊이 제한 등 "선택적으로 읽기"를 유도하는 기능을 제공하지 않는다.
- **확률적 기능을 쓰지 않는다** — 임베딩 검색이나 LLM 판단에 의존하지 않고, 결정론적 조회만 제공한다.

## 3. 파일과 프로젝트 구조

- **프로젝트 루트는 git 저장소 루트다.** 모든 문서 경로는 이 루트 기준의 상대 경로이며, 어느 하위 디렉토리에서 실행해도 같은 경로로 해석된다. 설정 파일을 두지 않는다 — 히스토리를 git 이 담당하기로 한 결정과 같은 근거다. git 저장소가 아니면 그 사실을 error 로 알린다.
- 문서 파일의 확장자는 `.kang` 이며, 항상 파일이다. 폴더는 확장자를 갖지 않는다.
- 디렉토리 계층이 곧 네임스페이스 계층이다.

```
docs/
  A.kang
  details/
    payment.kang
    free-item.kang
```

### frontmatter

| 키 | 필수 | 설명 |
|---|---|---|
| `description` | 필수 | 문서 목록 조회 시 이 문서를 고르기 위한 설명 |

문서의 식별자는 파일 경로 하나뿐이다. 별칭을 두지 않는다 — import에 쓸 수 없는 두 번째 이름은 "개념의 주인은 하나"에 위배된다.

### topic 밖에는 내용을 두지 않는다

frontmatter 블록, `import` 줄, `keyword` 선언 줄, 빈 줄 외에 **topic 밖에 오는 모든 줄은 error** 다. 문서 제목(`#`)이나 서문 단락도 여기 포함된다.

근거는 세 가지이며 전부 같은 곳을 가리킨다.

- topic 밖의 글은 어떤 **rev 해시에도 들어가지 않는다.** 바뀌어도 아무 참조처가 깨지지 않으므로 SoT 추적 밖이다.
- `kang show` 로 **볼 수 없다.** 조회 단위가 문서와 topic 뿐이므로 LLM 이 원본을 보지 않는다는 원칙 아래서는 존재하지 않는 것과 같다.
- 그 줄의 백틱은 4.2 상 심볼 참조인데 **가리킬 주소가 없다.** `kang refs` 의 출력 형식(6.3)은 `docs/A#topic이름` 이라 문서 레벨 참조를 표현할 수 없다.

문서 제목은 파일 경로가, 서문은 frontmatter `description` 이 이미 담당한다. 마크다운에서 이관할 때 서문에 실제 내용이 있으면 topic 으로 승격시킨다.

## 4. 문법

### 4.1 기호 체계

| 기호 | 의미 | 예 |
|---|---|---|
| `/` | 경로 구분 | `` `docs`/`details`/`payment` `` |
| `.` | 키워드 진입 및 키워드 계층 | `` `docs`/`A`.`결제수단`.`카드` `` |
| `#` | topic | `` `docs`/`A`#`결제의 방법` `` |
| `!` | exception | `` `docs`/`A`!`무료 상품에 대한 청구서` `` |

### 4.2 백틱 규칙

- 본문과 선언부의 모든 백틱은 **심볼 참조**다.
- 문자 그대로의 백틱은 `` \` `` 로 이스케이프한다.
- 코드 펜스(``` ``` ```) 내부는 예외로 두어 심볼 해석을 하지 않는다.

### 4.3 keyword

**그 프로젝트의 도메인 특수 용어**를 선언한다. 선언한 파일이 그 개념의 owner이며, 한 줄 정의를 반드시 제공해야 한다.

```
keyword `결제`: 사용자가 상품 대금을 지불하는 행위 #`결제의 상세`
keyword `결제일`: 실제 대금이 처리되는 날짜
keyword `결제수단`.`카드`: 카드를 사용한 결제
keyword `금액`: 청구되는 원화 액수 // iknow `docs`/`B`.`금액`
```

- 한 줄 정의는 필수다. 상세 설명이 필요하면 `#`로 topic을 연결한다(선택).
- 파일 최상단에 모아 쓰기를 권장하나 여러 번 등장할 수 있다.
- 하위 키워드는 `.`로 계층을 표현한다. 상위 키워드는 같은 파일에서 정의했거나 import한 것이어야 한다.

#### 무엇을 keyword 로 선언하나

`id`·`name`·`status`·`path` 처럼 일반 소프트웨어에서 통용되는 명사는 **선언하지 않는다.** 사람도 LLM 도 그 정도는 문맥으로 안다.

대상은 `epoch`·`승격` 처럼 **프로젝트를 아는 사람에게 즉시 특정 개념을 떠올리게 하는 용어**다. 이런 용어가 두 곳에서 다른 뜻으로 정의되는 것을 막는 것이 keyword 의 목적이다.

과잉 선언은 스스로 처벌된다. 일반 명사를 keyword 로 선언하면 그것을 언급하는 모든 문서가 `import` 를 해야 하므로 즉시 성가시고, 그래서 아무도 하지 않는다.

#### 동의어를 두지 않는다

같은 개념을 가리키는 다른 표기를 선언하는 문법은 **없다.** 이름은 정확히 하나다.

한때 `also` 문법을 검토했으나 뺐다. 동의어는 owner 가 **남이 쓸 변형을 미리 예견해야** 작동하는데, 예견할 수 있었다면 애초에 두 이름이 생기지 않았을 것이다. 즉 분열을 막는 것이 아니라 이미 벌어진 분열을 기록할 뿐이다. 그리고 처음부터 kang 으로 설계하면 변형이 생길 자리가 없다 — 본문의 모든 백틱이 심볼로 해석되므로, 다른 이름을 쓰면 그 자리에서 미해결 심볼 error 가 난다.

마크다운 코퍼스를 이관할 때 만나는 기존 변형은 이관 과정에서 정본 하나로 통합한다. 문법으로 수입하지 않는다.

#### 계층과 이름 충돌

**전체 경로가 같을 때만 충돌이다.** `결제`.`상태` 와 `구독`.`상태` 는 서로 다른 이름이므로 `iknow` 가 필요 없다. 계층이 존재하는 이유가 그것이다.

### 4.4 iknow

서로 다른 파일이 같은 이름의 심볼을 선언할 때, 각 파일이 나머지 전부의 존재를 인지하고 있음을 명시한다.

```
keyword `금액`: 청구되는 원화 액수 // iknow `docs`/`B`.`금액`, `docs`/`C`.`금액`
```

- keyword 선언, topic 헤딩, exception 선언 세 자리에 붙는다.
- 쉼표로 여러 대상을 나열한다.
- N개 파일이 같은 이름을 선언하면 N개 파일 모두가 나머지 전부를 명시해야 한다. 하나라도 빠지면 error 이며, 누락된 파일 경로를 진단에 전부 명시한다.

**`iknow` 는 참조가 아니라 부인(disavowal)이다.** "저기 같은 이름이 있다는 걸 알고, 나는 그것을 쓰지 않는다" 는 선언이다. 여기서 세 가지가 따라온다.

- **import 간선을 만들지 않는다.** 순환 검사 대상이 아니므로 상호 명시가 순환 error 를 유발하지 않는다. 쓰지 않겠다고 명시한 것을 import 하면 unused import error 가 나는 자기모순도 생기지 않는다.
- **경로와 상호성은 검증한다.** 대상 파일과 심볼이 실재해야 하고, 상대도 나를 `iknow` 해야 한다. **이름 해석 층위에서는** "미선언 참조는 에러" 에 구멍을 뚫지 않는다 — 검사받지 않는 것이 없고, 다만 그래프 간선이 아닐 뿐이다.
- **다만 SoT 층위에서는 구멍이 맞다.** 남의 정의를 자기 문서에 복제한 뒤 `iknow` 로 "다른 뜻이다" 라고 선언하면 합법이고, 그 복제본은 rev 추적에서 영구히 벗어난다. 원본이 바뀌어도 깨지지 않는다. 컴파일러는 뜻이 같은지 판정할 수 없으므로(8절) 막을 방법이 없다. **알고 감수하는 한계다.**
- **rev 핀을 갖지 않는다.** 상대의 정의가 무엇인지는 나와 무관하다. 내가 아는 것은 그 이름이 거기 있다는 사실뿐이고, 정의가 바뀌어도 그 사실은 변하지 않는다. 이름이 바뀌면 대상이 사라져 미해결 심볼 error 가 난다.

### 4.5 topic

`##` 로 시작하며, 파일 안에서 **완결성을 갖는 독립 단위**다. 같은 파일의 다른 topic과는 무관하다.

```
## 결제의 방법

사용자는 `결제수단` 으로 `결제` 를 한다.
```

`// uncoded` modifier를 붙이면 대응 코드가 없는 것이 정상인 topic으로 표시된다.

```
## 조직의 문서 검토 절차 // uncoded
```

### 4.6 exception / cover

정책의 예외를 선언하고, 다른 문서가 그 예외를 다루는 정책임을 명시한다. topic 최하단에 위치하기를 권장한다.

```
## 결제 청구서와 결제의 관계

모든 `청구서` 는 `결제` 에 의해 생겨난다.

exception `무료 상품에 대한 청구서`
exception `해외 결제` pending
```

```
## 무료상품 결제일 때 청구서

무료상품은 청구서 레코드 없이 0원 `결제` 기록만 남긴다.

cover `무료상품 청구서 예외`
```

`pending`은 "예외의 존재는 알지만 정책이 아직 결정되지 않았다"를 뜻한다.

### 4.7 import

파일 최상단에 작성한다. 컴파일러가 topic별 실제 사용 심볼을 추적하여 완결성을 보장한다.

```
import `docs`/`A`.`결제` as `A 결제` rev "a3f9c1"
import `docs`/`A`.`청구서` as `A 청구서` rev "c40d8a"
import `docs`/`A`#`상품의 정보` as `A 상품 정보` rev "7b21e0"
import `docs`/`details`/`payment`!`무료 상품에 대한 청구서` as `무료상품 청구서 예외` rev "e91b04"
```

- 외부로 노출되는 심볼은 **keyword / topic / exception** 세 종류다.
- 한 줄에 하나씩 쓴다. 그룹 문법을 두지 않는다 — rev 핀이 심볼마다 붙으므로 묶어서 절약되는 것은 경로 접두사뿐이다.
- `as` 로 alias를 지정한다.
- 한 심볼에 두 개 이상의 alias를 붙이는 것은 에러다. 하나의 개념이 여러 이름을 갖는 것을 막는다.
- **세 종류 모두 `rev` 핀이 필수**다 (4.8 참조).

### 4.8 rev 핀

import는 심볼의 **이름뿐 아니라 내용**에 대해서도 고정된다. 참조 시점의 내용 해시를 `rev`로 기록하고, 대상이 바뀌면 컴파일 에러가 발생하여 재검토를 강제한다.

`Cargo.lock`, `go.sum`, git submodule의 커밋 핀과 같은 원리다. 이것이 두 문제를 동시에 기계적으로 잡는다.

- **SoT 분열** — 상위 정책이 바뀌면 그것을 import한 하위 정책이 전부 깨진다. 옛 정책을 전제로 쓰인 문서가 방치될 수 없다.
- **코드-문서 불일치** — 문서가 바뀌면 그것을 참조하는 코드가 전부 깨진다 (v2, `V0003`).

해시 산출 규칙:

| 대상 | 해시 입력 |
|---|---|
| keyword | 한 줄 정의 텍스트 |
| topic | topic 본문 (헤딩 포함, 선언 줄 제외 — 아래) |
| exception | **그 예외를 선언한 topic 의 본문** (같은 경계 규칙) |

exception 은 본문이 없지만 의미는 **그것이 선언된 topic 의 맥락**에서 나온다. 맥락이 바뀌면 그 예외를 다루는 정책도 다시 봐야 하므로, 선언 topic 의 해시를 핀한다. 이름만 바뀌는 경우는 미해결 심볼 error 가 별도로 잡는다.

한 topic 이 exception 을 여러 개 선언하면 전부 같은 해시를 갖는다. 그 topic 이 바뀌면 모든 커버 문서가 깨진다 — 맥락이 바뀌었으니 전부 다시 봐야 하는 것이 맞다.

**topic 본문의 경계** — `exception`·`cover` 줄과 `// iknow`·`// uncoded` modifier 는 **본문에서 제외한다.** 선언이지 서술이 아니기 때문이다.

포함하면 한 topic 에 예외를 하나 더 추가하는 순간 그 topic 의 다른 예외를 커버하던 무관한 문서가 전부 깨진다. 어떤 문서가 `cover` 줄을 넣는 것만으로 자기 topic 해시가 바뀌어 자기를 참조하던 문서들이 연쇄로 깨지는 일도 생긴다. 핀이 잡아야 하는 것은 **의미를 담은 서술**이지 선언의 개수가 아니다.

- 정규화 후 해시한다: 앞뒤 공백 제거, 줄 끝 공백 제거, 연속 빈 줄 축약.
- SHA-256의 앞 6자리 hex를 사용한다. 사람이 눈으로 비교할 수 있는 길이여야 한다.

#### 새 import에 핀을 붙이는 법

핀을 손으로 계산할 수는 없다. **핀 없이 import 를 쓰고 `kang bless` 가 삽입한다.**

```
1. import `docs`/`A`.`결제` as `A 결제`     ← 핀 없이 쓴다
2. kang build → error "핀 없음"
                fix: kang bless docs/B --import 'docs/A.결제'
3. kang bless docs/B --import 'docs/A.결제' → 핀 삽입
```

`bless` 는 핀이 있으면 갱신하고 **없으면 삽입한다.** 더미 해시를 손으로 적는 의식이 생기지 않는다.

첫 핀도 의미를 갖는다. import 를 쓴 사람은 그 대상을 읽었어야 경로를 쓸 수 있으므로, 첫 핀은 "내가 이 상태를 보고 참조했다" 를 기록한다. 그리고 새 우회로가 되지도 않는다 — 핀을 지워서 검토를 회피할 바에는 그냥 `bless` 하면 되므로 더 쉬운 길이 아니다.

## 5. 컴파일 규칙

`kang build`는 기본값이 **error**다. 통과하지 못한 문서는 어떤 CLI 명령으로도 출력되지 않는다.

### 5.1 심볼 규칙

| 상황 | 결과 |
|---|---|
| 본문의 백틱 심볼이 선언·import되지 않음 | error |
| import했으나 어떤 topic에서도 사용하지 않음 | error (unused import) |
| 한 심볼에 두 개 이상의 alias | error |
| import의 `rev` 핀이 대상의 현재 해시와 불일치 | error — 대상 경로와 `kang bless` 인자 형식을 출력. 무엇이 바뀌었는지는 `git diff`가 보여준다 |
| import에 `rev` 핀이 없음 (세 종류 모두) | error — `kang bless` 가 삽입한다 (4.8) |
| 서로 다른 파일이 같은 이름의 심볼을 선언 (iknow 없음) | error — 관련된 모든 파일 경로를 로그에 명시 |
| `iknow` 가 관련 파일 전체를 상호 명시하지 않음 | error — 누락된 파일 경로를 로그에 명시 |
| `iknow` 대상 파일이나 심볼이 존재하지 않음 | error |
| import 그래프에 순환 존재 | error — 순환 체인 전체를 출력하고 공통 개념 추출을 안내 |

`iknow`는 keyword / topic / exception 세 심볼 모두에 동일하게 적용된다. N개 파일이 같은 이름을 선언하면 N개 파일 모두가 나머지 전부를 `iknow`로 명시해야 한다. **`iknow` 는 import 간선을 만들지 않으므로 상호 명시가 순환 error 를 유발하지 않는다** (4.4).

이름 충돌 판정은 **전체 경로 기준**이다. `결제`.`상태` 와 `구독`.`상태` 는 다른 이름이다 (4.3).

### 5.1.1 진단 출력

컴파일이 실패하면 에이전트가 보는 것은 **진단이 전부**다. 진단을 보고 스스로 고치지 못하면 도구가 무용지물이므로, 출력 모양을 여기서 못박는다.

세 요소가 항상 있다.

- **관련 위치 전부.** 한 곳만 보여주면 나머지를 찾아 헤맨다.
- **왜 문제인지 한 문장.** 규칙을 모르는 에이전트도 판단할 수 있어야 한다.
- **그대로 적용 가능한 `fix`.** 셸 명령이면 인용까지 포함한다.

**미해결 심볼**

```
error[K001]: 선언되지 않은 심볼 — `승격`

  docs/policy/regression.kang:22   본문에서 참조

  이 문서는 `승격` 을 선언하지도 import 하지도 않았습니다.
  같은 이름을 선언한 문서가 하나 있습니다: docs/core/baseline

  같은 개념이라면 import 하세요. 다른 개념이라면 이 문서에서
  keyword 로 선언하고 양쪽에 iknow 를 붙이세요.

  fix (같은 개념일 때, 순서대로):
    [edit]  docs/policy/regression.kang
            import 블록에 `` import `docs`/`core`/`baseline`.`승격` `` 추가
    [shell] kang bless docs/policy/regression --import 'docs/core/baseline.승격'
```

**`iknow` 누락**

```
error[K012]: 같은 이름의 심볼이 여러 파일에서 선언됨 — `epoch`

  docs/core/lease.kang:14   여기서 선언
  docs/core/draft.kang:8    여기서도 선언

  두 문서가 서로의 존재를 모릅니다. 다른 뜻이라면 각 선언 뒤에
  iknow 를 붙여 상호 명시하세요. 같은 뜻이라면 한쪽을 지우고
  다른 쪽을 import 하세요.

  fix (다른 개념일 때):
    [edit]  docs/core/lease.kang
            keyword `epoch` 선언 뒤에 ``// iknow `docs`/`core`/`draft`.`epoch` `` 추가
    [edit]  docs/core/draft.kang
            keyword `epoch` 선언 뒤에 ``// iknow `docs`/`core`/`lease`.`epoch` `` 추가
```

`fix` 는 **순서 있는 목록**이며 각 항목은 종류를 갖는다.

| 종류 | 문법 | 예 |
|---|---|---|
| `[edit]` | **문서 문법.** 백틱을 쓴다 (4.2) | ``// iknow `docs`/`B`.`금액` `` |
| `[shell]` | **CLI 문법.** 백틱을 쓰지 않고 인용한다 (6.0) | `kang bless docs/B --import 'docs/A.결제'` |

두 문법을 섞으면 안 된다. `[edit]` 를 CLI 문법으로 쓰면 삽입된 줄이 4.2 를 위반하고, `[shell]` 을 문서 문법으로 쓰면 셸에서 명령 치환으로 터진다.

**`fix` 는 줄 번호를 좌표로 쓰지 않는다.** 에이전트가 첫 `fix` 를 적용하면 줄이 밀려 두 번째 `fix` 의 줄 번호가 틀린다. 무엇을 고칠지는 심볼과 선언으로 지정한다 ([ADR-0003](../../docs/adr/0003-symbolic-addressing-not-line-numbers.md)). 줄 번호는 `location` 에만 나타나며 그것은 "여기를 보라" 는 표시일 뿐 다음 명령의 인자가 아니다.

**`rev` 불일치**

```
error[K021]: rev 핀이 대상의 현재 내용과 다름 — `docs/core/payment#결제의 방법`

  docs/billing/invoice.kang:3   핀 a3f9c1, 현재 7b21e0

  참조한 뒤 대상이 바뀌었습니다. 무엇이 바뀌었는지는
  git diff docs/core/payment.kang 으로 확인하세요.
  이 문서가 여전히 맞는지 확인한 뒤 핀을 갱신하세요.

  fix:
    [shell] kang bless docs/billing/invoice --import 'docs/core/payment#결제의 방법'
```

나머지 규칙도 같은 모양을 따른다. `code` 는 규칙마다 고정이며, 에이전트가 코드로 분기할 수 있어야 한다.

### 5.2 exception 상태 기계

| exception 상태 | cover 있음 | cover 없음 |
|---|---|---|
| 일반 | 통과 | **error** — 이 예외를 커버하는 정책이 없음 |
| `pending` | **error** — 미결정이라 선언했으나 커버가 존재함 | **warn** — 통과 |

한 exception을 둘 이상의 topic이 cover하면 error다. 예외 하나에 정책 하나를 강제한다.

### 5.3 순환 검출의 단위

순환 검출은 **파일 단위**로 한다 (5.1). 파일 그래프가 DAG 면 topic 그래프도 DAG 다 — topic 간선 T→U 는 반드시 file(T)→file(U) 를 동반하므로 파일 단위 금지가 더 강하다.

이 DAG 보장 위에 v2 의 참조 전파가 서 있다(`V0003` 2절). v1 에는 전파의 소비자가 없으므로 그래프 값을 남기지 않고 순환만 검출한다.

## 6. CLI

```
kang init                               에이전트 진입점과 첫 문서 생성
kang build                              컴파일 및 검증
kang bless    <문서> --import <심볼>    rev 핀 갱신·삽입
kang list     [경로]                    문서 목록과 description
kang keywords [경로]                    키워드 목록
kang refs     <키워드>                  키워드를 참조하는 topic
kang show     <문서|토픽>               문서/토픽 조회 (YAML)
kang inspect                            코드 대조 (v2)
```

`kang inspect` 는 v2 다. v1 바이너리에서 호출하면 "v2 기능이며 아직 구현되지 않았다" 를 명시하고 종료 코드 3 으로 끝낸다. 존재하지 않는 명령처럼 보이면 에이전트가 철자를 의심하며 재시도한다.

**종료 코드**

| 코드 | 의미 |
|---|---|
| 0 | 성공 |
| 1 | 컴파일 error 존재 |
| 2 | 사용법 오류 (알 수 없는 명령, 인자 부족) + 환경 오류 (git 저장소 아님) |
| 3 | v2 기능 호출 |

에이전트는 종료 코드로 분기한다. 1과 2를 구분해야 "문서를 고쳐야 한다" 와 "명령을 잘못 썼다" 를 나눌 수 있다.

**사용법 오류에는 `--help` 를 함께 출력하지만 환경 오류에는 출력하지 않는다.** git 저장소가 아닌 것은 명령을 잘못 쓴 게 아니다. 여기서 help 를 보여주면 에이전트가 철자를 의심하며 재시도한다. `git init` 지시만 낸다.

예외가 어디서 커버되는지는 별도 명령을 두지 않는다. `kang show`가 정의 파일에서 `coveredBy`로 이미 출력한다.

### 6.0 CLI 인자 문법

**인자에는 백틱을 쓰지 않는다.** 백틱은 셸에서 명령 치환이며, 비대화형 호출에서도 터진다. LLM 에이전트가 kang 을 부르는 방식이 정확히 비대화형이므로 조용한 오작동이 된다.

```
kang refs docs/A.결제
kang show 'docs/A#결제의 방법'
kang bless docs/B --import 'docs/A.결제 수단'
```

- 문서 본문의 백틱은 유지한다 (4.2). CLI 인자는 별개 문법이며 `/`·`.`·`#`·`!` 만으로 파싱된다.
- 공백이 있는 이름은 셸 인용이 필요하다. 이는 셸의 정상 규약이다.
- **`kang build` 의 `fix` 문자열은 인용을 붙여 출력한다.** 에이전트가 복사해 그대로 실행할 수 있어야 하며, 인용 여부를 스스로 판단하게 두면 틀린다.

### 6.1 `kang init` — 에이전트 진입점

kang 의 주 사용자는 **다른 프로젝트에서 일하는 LLM 에이전트**다. 그런데 "LLM 은 원본을 보지 않는다" 는 원칙은 강제할 수 없다 — 에이전트는 `.kang` 파일을 그냥 읽을 수 있다.

그래서 이 원칙은 **에이전트가 kang 의 존재와 사용법을 알고 있을 때만** 성립한다. 저장소에 `.kang` 파일만 있으면 에이전트는 그게 무엇인지 모르고 `cat` 한다. 그리고 `cat` 으로 읽은 `.kang` 은 import 간접 참조 때문에 **마크다운보다 읽기 나쁘다.** 도구를 도입하고 오히려 나빠지는 것이다.

`kang init` 이 그 간극을 메운다. 네 파일을 쓴다.

| 파일 | 역할 |
|---|---|
| `.claude/skills/kang/SKILL.md` | Claude 용 스킬. 케이스별 기대 동작 |
| `AGENTS.md` | Codex 용. **내용을 복제하지 않고 `SKILL.md` 를 가리킨다** |
| `CLAUDE.md` | 한 줄 진입점 — "이 프로젝트의 문서는 kang 으로 유지보수된다. kang 스킬을 사용하여야 한다" |
| 첫 `.kang` 문서 | frontmatter 가 채워진 템플릿 |

**저장소에 커밋되는 프로젝트 스코프 파일로 만든다.** 전역 스킬 설치를 요구하면 설치 단계가 늘고 clone 하는 사람마다 상태가 달라진다. 저장소에 들어 있으면 clone 하는 순간 따라온다.

**스킬 내용은 `SKILL.md` 한 곳에만 있다.** `AGENTS.md` 와 `CLAUDE.md` 는 그것을 가리키기만 한다. 같은 내용을 두 파일에 복제하면 kang 이 막으려는 바로 그 SoT 분열이 kang 자신의 도구에서 일어난다.

기존 `CLAUDE.md`·`AGENTS.md` 는 **덮어쓰지 않는다.** 섹션만 덧붙이고, 이미 kang 섹션이 있으면 건너뛴다.

**`kang init` 은 git 저장소를 요구하지 않는다.** 프로젝트 루트가 git 루트라는 규칙(3절)은 문서를 해석하는 명령에만 적용된다. `init` 은 갓 만든 디렉토리에서 실행되는 첫 명령이므로, git 저장소가 아니면 현재 디렉토리를 루트로 삼아 파일을 만들고 **`git init` 을 안내하는 문구를 함께 출력한다.** 여기서 종료 코드 2로 죽으면 T0 에서 벽을 만든다.

#### 스킬 내용

케이스별로 기대 동작을 기술한다.

- **정책을 조회할 때** — `kang keywords` 로 개념을 훑고 `kang refs` 로 좁힌 뒤 `kang show` 로 읽는다. `.kang` 파일을 직접 열지 않는다. `show` 가 상위 정책을 전부 평탄화해 주므로 링크를 따라갈 필요가 없다.
- **정책을 쓸 때** — 먼저 `kang show` 로 관련 정책을 읽는다. 읽은 내용을 자기 문장으로 다시 쓰지 않고 `import` 로 참조한다. 서술을 복제하면 SoT 가 갈라진다 ([ADR-0002](../../docs/adr/0002-flatten-on-read-import-on-write.md)).
- **컴파일이 실패했을 때** — 진단의 `fix` 를 그대로 적용한다. 셸 명령은 인용까지 포함되어 출력되므로 복사해 실행하면 된다.
- **개념 이름을 바꿀 때** — 참조하던 모든 문서가 깨진다. 전부 고친 뒤 각각 `kang bless` 한다. 묘비를 남기지 않는다 ([ADR-0001](../../docs/adr/0001-no-tombstones-for-retired-terms.md)).
- **코드를 고칠 때** (v2) — 언어별 애노테이션 가이드. 어떤 정책을 구현하는 코드인지 표시하고 rev 핀을 맞춘다.

### 6.2 `kang bless`

rev 핀을 갱신하거나 삽입하는 유일한 명령이다.

```
kang bless <문서> --import <심볼>
```

해당 참조를 검토했음을 선언한다. 핀이 있으면 갱신하고 없으면 삽입한다 (4.8).

- **주소는 심볼이다. 줄 번호를 쓰지 않는다.** 정상 워크플로가 "문서를 고친 뒤 bless" 이므로 줄이 밀리고, 밀린 줄 번호로 갱신하면 엉뚱한 핀을 조용히 바꾼다. 근거는 [ADR-0003](../../docs/adr/0003-symbolic-addressing-not-line-numbers.md).
- 한 파일 안에서 같은 심볼을 두 번 import 하는 것은 이미 error 이므로 심볼 주소는 유일하게 결정된다.
- **변경의 성격을 판단하는 옵션을 두지 않는다.** "이 변경은 사소하다"는 범주 판단이며, 이는 kang이 제거하려는 LLM 판단 그 자체다. `bless`가 주장하는 것은 범주가 아니라 "검토했다"는 사실뿐이다.
- **일괄 해제 수단이 없다.** 대상을 고치는 비용이 영향 범위에 비례하는 것은 의도된 설계다. 50곳이 참조하는 개념을 바꾸면 50곳을 확인해야 한다.
- 사소한 서식 변경은 4.8의 정규화 규칙이 흡수하므로 핀이 깨지지 않는다.
- 의미가 바뀐 변경에 별도 선언은 필요 없다. **아무것도 하지 않는 것이 기본 상태**이며, 참조처는 각 문서를 실제로 고친 뒤 `bless`로 해제한다.

### 6.3 목록 출력 형식

목록형 명령(`list`, `keywords`, `refs`)은 **한 라인이 의미론적 완결성을 갖는 형식** 하나만 출력한다. 경로는 항상 전체 경로이며 계층 축약을 쓰지 않는다. LLM이 경로를 조립하다 틀리는 것을 막는다.

```
$ kang list docs
docs/A: {description}
docs/details/payment: {description}
docs/details/free-item: {description}
```

사람이 읽기 좋은 계층형 출력을 별도로 제공하지 않는다. 이 도구의 독자는 LLM이고, 출력 형식이 둘이면 코드 경로와 테스트가 둘이 된다.

### 6.4 `kang show`

kang의 핵심 명령. 원본 파일을 그대로 보여주는 대신 관계 정보를 임베딩한 YAML을 출력한다.

포함되는 정보:

- 해당 파일이 정의한 키워드와, 그 키워드를 참조하는 topic 목록
- 해당 파일이 참조하는 키워드와, 그것을 정의한 파일
- 해당 파일이 정의한 예외와 그 커버 내용
- 해당 파일이 커버하는 예외
- 각 topic이 참조하는 키워드와 topic을 **재귀적으로 임베드**

출력 스키마:

```yaml
path: docs/B
keywords:                        # 이 파일이 정의한 키워드
  - name: 결제수단.카드
    description: 카드를 사용한 결제
    referencedBy:
      - docs/C#무료결제의 구성요소
referencingKeywords:             # 이 파일이 참조하는 키워드
  - name: 결제
    path: docs/A
    description: 사용자가 상품 대금을 지불하는 행위
exceptions:                      # 이 파일이 정의한 예외
  - name: 카드 수단 무료 결제
    pending: false
    coveredBy: docs/C#무료결제의 구성요소
    topic: |
      ## 무료결제의 구성요소

      무료결제는 `청구서` 와 `결제 내역` 레코드는 없고...
covers:                          # 이 파일이 커버하는 예외 (없으면 생략)
  - name: ...
    path: ...
    topic: |
      ...
topics:
  - name: 카드 결제
    uncoded: false
    topic: |
      ## 카드 결제

      `결제`를 하기 위한 수단 중 `결제수단`.`카드` 에 대한 설명이다.
    references:
      keywords:
        - name: 결제
          description: 사용자가 상품 대금을 지불하는 행위
          referencedBy:
            - docs/B#카드 결제
            - docs/C#무료결제의 구성요소
      topics:
        - name: docs/A#결제의 구성 요소
          uncoded: false
          topic: |
            ## 결제의 구성 요소

            `결제`는 `청구서` 와 `결제 내역` 으로 이루어져 있다.
          references:
            ...
```

출력 규칙:

- 모든 경로는 계층 축약 없이 **전체 경로**로 표기한다.
- 멀티라인 본문은 literal scalar(`|`)를 사용한다. folded scalar(`>`)는 개행이 접혀 마크다운 구조가 깨진다.
- **중복 제거** — 같은 topic이나 키워드가 여러 경로로 도달되면 최초 1회만 전개하고, 이후에는 경로 참조로 대체한다.
- 출력 분량이나 토큰 규모를 표시하지 않는다. 깊이를 제한하는 옵션도 두지 않는다.

#### 깊이 폭발 (v1 미구현, 모양만 확정)

import 폐포가 깊으면 `show` 한 번이 프로젝트 전체를 뱉고, 컨텍스트를 넘기면 잘린 입력으로 조용히 틀린 답이 나온다. v1 에서는 다루지 않는다 — 임계값을 데이터 없이 고르면 추측이고, 도그푸딩과 실제 코퍼스에서 진짜 숫자가 나온다.

손댈 때의 모양은 지금 못박는다.

- **읽기 시점이 아니라 빌드 시점에 막는다.** `show` 가 "너무 크니 줄여 읽어라" 라고 하면 그것이 선택권이다. 대신 어떤 topic 의 import 폐포가 N개를 넘으면 `kang build` error 로 낸다. LLM 은 선택지를 보지 못하고 사람이 문서 구조를 고친다.
- **메시지는 "출력이 크다" 가 아니라 "이 문서가 참조하는 정책이 너무 많다" 다.** 컨텍스트 한계는 소비자마다 다르므로 진단이 그것에 종속되면 안 된다. 구조 문제로 말해야 다른 규칙들과 같은 층위에 놓인다.

즉 출력 제한이 아니라 **구조 린트**다. 한 정책이 10개 상위 정책에 의존한다는 것은 대개 그 정책이 너무 많은 일을 하고 있다는 신호다.

### 6.5 조회 예시

```
$ kang refs docs/A.결제
docs/A#결제의 방식
docs/A#결제의 종류
docs/details/payment#결제의 방법
```

## 7. 코드 연동 (v2)

`kang inspect` 로 코드와 문서를 대조하는 설계는 **`V0003-kang-v2-code-integration.md`** 에 있다. v1 구현 대상이 아니므로 여기 두지 않는다.

v1 이 남기는 접점은 둘이다. `kang inspect` 를 호출하면 v2 안내와 함께 종료 코드 3 으로 끝낸다(6절). 그리고 `// uncoded` 문법은 v1 파서가 인식하되 검사는 v2 가 한다.

## 8. 비목표와 한계

- **kang은 "옳음"을 검증하지 못한다.** 자연어이기 때문이다. 두 정책이 서로 모순되는지, `cover`가 실제로 그 예외를 다루는지, 애노테이션이 붙은 코드가 정책대로 동작하는지는 판정할 수 없다. 마지막 것은 테스트의 몫이다.
- **대신 "재검토했음"은 100% 기계적으로 강제한다.** 실무에서 발생하는 문제는 "누가 틀린 판단을 했다"가 아니라 "아무도 다시 보지 않았다"이며, rev 핀이 이것을 결정론적으로 잡는다.
- 역할 분담은 다음과 같다.

| | 주체 | 방식 |
|---|---|---|
| 판단 | 사람 / LLM | 결과를 선언으로 고정한다 — `pending`, `iknow`, `uncoded`, `rev` 핀 |
| 검사 | 컴파일러 | 선언과 실제의 어긋남을 100% 기계적으로 검출한다 |
- **자연어 검색을 제공하지 않는다.** 임베딩이나 LLM 판단은 확률적이므로 신뢰할 수 없다. `kang keywords`로 개념을 훑고 `kang refs`로 좁히는 결정론적 탐색이 검색을 대신한다. 키워드가 곧 색인이다.
- **버전 관리를 하지 않는다.** git이 담당한다. 언어에는 deprecated 표현 수단이 없다.

## 9. 미결정 사항

- 언어별 애노테이션의 이름과 인자 형태, 심볼 인덱스 파일의 포맷 — v2 착수 시 결정.
- 에러 메시지 포맷 — LLM이 자가 수정할 수 있도록 수정 위치와 방법을 명시해야 한다. 구현 시 상세 설계.
