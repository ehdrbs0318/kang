# V0001 — kang 언어 설계

문서 전용 언어 `kang`의 언어 명세와 CLI 계약을 정의한다.

---

## 1. 배경

정책 문서를 마크다운으로 관리하면서 두 가지 문제가 생겼다.

1. **SoT 분열** — 한 개념의 "정답"이 여러 문서에 흩어지고, 문서마다 다른 내용을 말한다. 원인은 이렇다. LLM 에이전트가 문서 A를 쓸 때, 관련 문서 B를 참조하지 못한 채 새 문서를 쓴다.
2. **코드-문서 불일치** — 문서를 쓰는 에이전트와 코드를 쓰는 에이전트가 다르다. 그래서 한쪽이 바뀌어도 다른 쪽이 따라 바뀌지 않는다.

핵심은 이것이다. 문제는 문서의 크기가 아니다. **한 개념에 대한 정답의 종류**가 늘어나는 것이 문제다. 문서가 커지는 비용은 받아들인다. 해결할 대상은 정답의 종류가 늘어나는 것이다.

## 2. 설계 원칙

- **개념의 주인은 하나** — 한 키워드는 정확히 한 파일이 정의한다. 중복은 컴파일 에러다.
- **참조는 명시적** — 다른 문서의 개념을 쓰려면 반드시 `import` 해야 한다. 선언하지 않은 참조는 에러다.
- **LLM은 원본을 보지 않는다** — LLM 은 CLI가 출력한 결과만 참조한다. 컴파일에 실패한 문서는 출력되지 않는다.
- **최신 버전만 존재한다** — override 문법이 없다. 정책을 바꾸려면 owner 파일을 직접 고쳐야 한다.
- **판단은 선언으로 고정한다** — 사람이나 LLM의 판단이 필요한 곳마다 선언 문법을 둔다. 판단은 한 번으로 끝난다. 그 뒤의 검사는 전부 기계적이다.
- **의도적 마찰** — 개념이 중복되거나 예외를 내버려 두면, kang 은 사용자를 귀찮게 한다. 이 귀찮음이 SoT 분열을 막는다.
- **LLM에게 덜 읽을 선택권을 주지 않는다** — 출력 분량 표시, 깊이 제한처럼 "선택적으로 읽기"를 유도하는 기능을 제공하지 않는다.
- **확률적 기능을 쓰지 않는다** — 임베딩 검색이나 LLM 판단에 의존하지 않는다. 결정론적 조회만 제공한다.

## 3. 파일과 프로젝트 구조

- **프로젝트 루트는 git 저장소 루트다.** 모든 문서 경로는 이 루트 기준의 상대 경로다. 어느 하위 디렉토리에서 실행해도 같은 경로로 해석된다. 설정 파일은 두지 않는다. 근거는 히스토리를 git 에 맡기기로 한 결정과 같다. git 저장소가 아니면, kang 은 그 사실을 error 로 알린다.
- 문서 파일의 확장자는 `.kang` 이다. 문서는 항상 파일이다. 폴더에는 확장자가 없다.
- 디렉토리 계층이 곧 네임스페이스 계층이다.

```
docs/
  A.kang
  details/
    payment.kang
    free-item.kang
```

### frontmatter

| 키 | 필수 | 설명 |
|---|---|---|
| `description` | 필수 | 문서 목록을 볼 때 이 문서를 고르는 데 쓰는 설명 |

문서의 식별자는 파일 경로 하나뿐이다. 별칭은 두지 않는다. 별칭은 import 에 쓸 수 없는 두 번째 이름이므로, "개념의 주인은 하나" 원칙을 어긴다.

### topic 밖에는 내용을 두지 않는다

topic 밖에 올 수 있는 줄은 frontmatter 블록, `import` 줄, `keyword` 선언 줄, 빈 줄뿐이다. **그 밖의 줄이 topic 밖에 오면 모두 error** 다. 문서 제목(`#`)과 서문 단락도 error 다.

근거는 세 가지이고, 셋 다 같은 결론으로 이어진다.

- topic 밖의 글은 어떤 **rev 해시에도 들어가지 않는다.** 그 글이 바뀌어도 깨지는 참조가 하나도 없다. 그래서 그 글은 SoT 추적에서 빠진다.
- `kang show` 로 **볼 수 없다.** 조회 단위는 문서와 topic 뿐이다. "LLM 이 원본을 보지 않는다" 원칙에서는, 볼 수 없는 글은 없는 글과 같다.
- topic 밖 줄의 백틱은 4.2 에 따라 심볼 참조인데, **가리킬 주소가 없다.** `kang refs` 의 출력 형식(6.3)은 `docs/A#topic이름` 이다. 이 형식으로는 문서 레벨의 참조를 나타낼 수 없다.

문서 제목은 파일 경로가 이미 맡는다. 서문은 frontmatter `description` 이 이미 맡는다. 마크다운 문서를 kang 으로 옮길 때 서문에 실제 내용이 있으면, 그 내용을 topic 으로 옮긴다.

## 4. 문법

### 4.1 기호 체계

| 기호 | 의미 | 예 |
|---|---|---|
| `/` | 경로 구분 | `` `docs`/`details`/`payment` `` |
| `.` | 키워드 진입 및 키워드 계층 | `` `docs`/`A`.`결제수단`.`카드` `` |
| `#` | topic | `` `docs`/`A`#`결제의 방법` `` |
| `!` | exception | `` `docs`/`A`!`무료 상품에 대한 청구서` `` |

### 4.2 백틱 규칙

- 본문과 선언부의 모든 백틱은 **심볼 참조**다.
- 백틱 문자 자체를 쓰려면 `` \` `` 로 이스케이프한다.
- 코드 펜스(``` ``` ```) 안은 예외다. 그 안에서는 심볼을 해석하지 않는다.

### 4.3 keyword

**그 프로젝트의 도메인 특수 용어**를 선언한다. 선언한 파일이 그 개념의 owner 다. 선언에는 한 줄 정의가 반드시 있어야 한다.

```
keyword `결제`: 사용자가 상품 대금을 지불하는 행위 #`결제의 상세`
keyword `결제일`: 실제 대금이 처리되는 날짜
keyword `결제수단`.`카드`: 카드를 사용한 결제
keyword `금액`: 청구되는 원화 액수 // iknow `docs`/`B`.`금액`
```

- 한 줄 정의는 필수다. 상세 설명이 필요하면 `#`로 topic을 연결한다(선택).
- 파일 맨 위에 모아 쓰기를 권장한다. 하지만 파일 안에 여러 번 나와도 된다.
- 하위 키워드는 `.`로 계층을 나타낸다. 상위 키워드는 같은 파일에서 정의했거나 import 한 것이어야 한다.

#### 무엇을 keyword 로 선언하나

`id`, `name`, `status`, `path` 처럼 일반 소프트웨어에서 흔히 쓰는 명사는 **선언하지 않는다.** 사람도 LLM 도 그런 명사는 문맥으로 안다.

선언 대상은 `epoch`, `승격` 처럼 **프로젝트를 아는 사람이 보면 바로 특정 개념을 떠올리는 용어**다. keyword 는 이런 용어가 두 곳에서 다른 뜻으로 정의되지 않게 막는다.

필요 이상으로 선언하면 그 비용이 바로 드러난다. 일반 명사를 keyword 로 선언하면, 그 명사를 쓰는 모든 문서가 `import` 를 해야 한다. 그러면 바로 번거로워지므로, 아무도 일반 명사를 선언하지 않는다.

#### 동의어를 두지 않는다

같은 개념을 다른 표기로 선언하는 문법은 **없다.** 이름은 정확히 하나다.

한때 `also` 문법을 검토했으나 뺐다. 동의어가 동작하려면 owner 가 **다른 사람이 쓸 변형을 미리 알아야** 한다. 미리 알 수 있었다면 처음부터 두 이름이 생기지 않았을 것이다. 즉 동의어는 분열을 막지 못하고, 이미 생긴 분열을 기록할 뿐이다. 그리고 처음부터 kang 으로 설계하면 변형이 생길 곳이 없다. 본문의 모든 백틱이 심볼로 해석되므로, 다른 이름을 쓰면 그 위치에서 바로 미해결 심볼 error 가 난다.

마크다운 문서 묶음(코퍼스)을 kang 으로 옮길 때 이미 있는 변형을 만나면, 옮기는 과정에서 정본 이름 하나로 합친다. 변형을 문법으로 받아들이지 않는다.

#### 계층과 이름 충돌

**전체 경로가 같을 때만 충돌이다.** `결제`.`상태` 와 `구독`.`상태` 는 서로 다른 이름이므로 `iknow` 가 필요 없다. 계층은 이런 충돌을 피하려고 있다.

### 4.4 iknow

서로 다른 파일이 같은 이름의 심볼을 선언할 때 쓴다. 각 파일은 같은 이름을 선언한 나머지 파일 전부를 안다고 명시한다.

```
keyword `금액`: 청구되는 원화 액수 // iknow `docs`/`B`.`금액`, `docs`/`C`.`금액`
```

- keyword 선언, topic 헤딩, exception 선언의 세 곳에 붙는다.
- 쉼표로 여러 대상을 나열한다.
- N개 파일이 같은 이름을 선언하면, N개 파일 모두가 나머지 전부를 명시해야 한다. 하나라도 빠지면 error 다. 진단은 빠진 파일 경로를 전부 보여 준다.

**`iknow` 는 참조가 아니다. 관계를 끊는 선언(disavowal)이다.** 뜻은 "저기 같은 이름이 있다는 것을 알고, 나는 그것을 쓰지 않는다" 이다. 이 성질에서 세 가지가 나온다.

- **import 간선을 만들지 않는다.** `iknow` 는 순환 검사 대상이 아니다. 그래서 상호 명시가 순환 error 를 만들지 않는다. 쓰지 않겠다고 밝힌 대상을 import 하면 unused import error 가 나는 모순도 생기지 않는다.
- **경로와 상호성은 검사한다.** 대상 파일과 심볼이 실제로 있어야 하고, 상대 파일도 나를 `iknow` 해야 한다. 이름 해석 수준에서는 "미선언 참조는 에러" 원칙에 빈틈을 만들지 않는다. 검사하지 않는 것은 없다. 다만 `iknow` 가 그래프 간선이 아닐 뿐이다.
  - **다만 SoT 수준에서는 빈틈이 맞다.** 다른 문서의 정의를 자기 문서에 복사한 뒤 `iknow` 로 "다른 뜻이다" 라고 선언하면 규칙상 문제가 없다. 그 복사본은 rev 추적에서 영구히 빠진다. 원본이 바뀌어도 복사본은 깨지지 않는다. 컴파일러는 두 뜻이 같은지 판단할 수 없으므로(8절) 이런 복사를 막을 방법이 없다. 알고 받아들이는 한계다.
- **rev 핀을 갖지 않는다.** 상대의 정의가 무엇인지는 나와 관계없다. 내가 아는 것은 그 이름이 거기 있다는 사실뿐이다. 정의가 바뀌어도 그 사실은 바뀌지 않는다. 이름이 바뀌면 대상이 없어지고, 미해결 심볼 error 가 난다.

### 4.5 topic

`##` 로 시작한다. topic 은 파일 안에서 **그 자체로 완결된 독립 단위**다. 같은 파일의 다른 topic 과는 관계가 없다.

```
## 결제의 방법

사용자는 `결제수단` 으로 `결제` 를 한다.
```

`// uncoded` modifier를 붙이면, 그 topic 은 대응하는 코드가 없는 것이 정상인 topic 으로 표시된다.

```
## 조직의 문서 검토 절차 // uncoded
```

### 4.6 exception / cover

정책의 예외를 선언하고, 다른 문서가 그 예외를 다루는 정책이라고 명시한다. 이 선언은 topic 맨 아래에 두기를 권장한다.

```
## 결제 청구서와 결제의 관계

모든 `청구서` 는 `결제` 에 의해 생겨난다.

exception `무료 상품에 대한 청구서`
exception `해외 결제` pending
```

```
## 무료상품 결제일 때 청구서

무료상품은 청구서 레코드 없이 0원 `결제` 기록만 남긴다.

cover `무료상품 청구서 예외`
```

`pending`은 "예외의 존재는 알지만 정책이 아직 결정되지 않았다"를 뜻한다.

### 4.7 import

파일 맨 위에 쓴다. 컴파일러가 topic 마다 실제로 쓰는 심볼을 추적해 완결성을 보장한다.

```
import `docs`/`A`.`결제` as `A 결제` rev "a3f9c1"
import `docs`/`A`.`청구서` as `A 청구서` rev "c40d8a"
import `docs`/`A`#`상품의 정보` as `A 상품 정보` rev "7b21e0"
import `docs`/`details`/`payment`!`무료 상품에 대한 청구서` as `무료상품 청구서 예외` rev "e91b04"
```

- 외부로 공개되는 심볼은 **keyword / topic / exception** 세 종류다.
- 한 줄에 하나씩 쓴다. 그룹 문법은 두지 않는다. rev 핀이 심볼마다 붙으므로, 묶어서 줄일 수 있는 것은 경로 앞부분뿐이다.
- `as` 로 alias를 지정한다.
- 한 심볼에 alias 를 두 개 이상 붙이면 에러다. 이 규칙은 한 개념이 여러 이름을 갖는 것을 막는다.
- **세 종류 모두 `rev` 핀이 필수**다 (4.8 참조).

### 4.8 rev 핀

import 는 심볼의 **이름뿐 아니라 내용**에도 고정된다. 참조한 시점의 내용 해시를 `rev`로 기록한다. 대상이 바뀌면 컴파일 에러가 나므로, 다시 검토할 수밖에 없다.

`Cargo.lock`, `go.sum`, git submodule의 커밋 핀과 같은 원리다. rev 핀은 두 문제를 동시에 기계적으로 잡는다.

- **SoT 분열** — 상위 정책이 바뀌면, 그 정책을 import 한 하위 정책이 전부 깨진다. 옛 정책을 전제로 쓴 문서를 그대로 둘 수 없다.
- **코드-문서 불일치** — 문서가 바뀌면, 그 문서를 참조하는 코드가 전부 깨진다 (v2, `V0003`).

해시 계산 규칙:

| 대상 | 해시 입력 |
|---|---|
| keyword | 한 줄 정의 텍스트 |
| topic | topic 본문 (헤딩 포함, 선언 줄 제외 — 아래) |
| exception | **그 예외를 선언한 topic 의 본문** (같은 경계 규칙) |

exception 은 본문이 없다. 하지만 exception 의 의미는 **그 exception 을 선언한 topic 의 맥락**에서 나온다. 맥락이 바뀌면 그 예외를 다루는 정책도 다시 봐야 한다. 그래서 선언한 topic 의 해시를 핀으로 쓴다. 이름만 바뀌는 경우는 미해결 심볼 error 가 따로 잡는다.

한 topic 이 exception 을 여러 개 선언하면, 그 exception 들은 전부 같은 해시를 갖는다. 그 topic 이 바뀌면 모든 cover 문서가 깨진다. 맥락이 바뀌었으므로 전부 다시 보는 것이 맞다.

**topic 본문의 경계** — `exception`, `cover` 줄과 `// iknow`, `// uncoded` modifier 는 본문에서 뺀다. 이 줄들은 선언이고, 서술이 아니기 때문이다.

이 줄들을 본문에 넣으면 문제가 생긴다. 한 topic 에 예외를 하나 더 추가하면, 그 topic 의 다른 예외를 cover 하던 관계없는 문서가 전부 깨진다. 또 어떤 문서가 `cover` 줄을 넣기만 해도 자기 topic 해시가 바뀐다. 그러면 그 topic 을 참조하던 문서들이 줄줄이 깨진다. 핀이 잡아야 하는 것은 **의미를 담은 서술**이다. 선언의 개수가 아니다.

- 정규화한 뒤 해시한다: 앞뒤 공백 제거, 줄 끝 공백 제거, 연속 빈 줄을 하나로 줄임.
- SHA-256의 앞 6자리 hex를 쓴다. 사람이 눈으로 비교할 수 있는 길이여야 하기 때문이다.

#### 새 import에 핀을 붙이는 법

핀은 손으로 계산할 수 없다. **import 를 핀 없이 쓰고, `kang bless` 가 핀을 넣는다.**

```
1. import `docs`/`A`.`결제` as `A 결제`     ← 핀 없이 쓴다
2. kang build → error "핀 없음"
                fix: kang bless docs/B --import 'docs/A.결제'
3. kang bless docs/B --import 'docs/A.결제' → 핀 삽입
```

`bless` 는 핀이 있으면 갱신하고 **없으면 삽입한다.** 그래서 더미 해시를 손으로 적는 절차가 생기지 않는다.

첫 핀에도 의미가 있다. import 를 쓴 사람은 그 대상을 읽어야 경로를 쓸 수 있다. 그래서 첫 핀은 "내가 이 상태를 보고 참조했다" 를 기록한다. 첫 핀은 검토를 피하는 새 방법도 되지 않는다. 핀을 지워서 검토를 피하는 것보다, 그냥 `bless` 하는 것이 더 쉽기 때문이다.

## 5. 컴파일 규칙

`kang build`는 기본값이 **error**다. 통과하지 못한 문서는 어떤 CLI 명령으로도 출력되지 않는다.

### 5.1 심볼 규칙

| 상황 | 결과 |
|---|---|
| 본문의 백틱 심볼이 선언·import되지 않음 | error |
| import했으나 어떤 topic에서도 사용하지 않음 | error (unused import) |
| 한 심볼에 두 개 이상의 alias | error |
| import의 `rev` 핀이 대상의 현재 해시와 불일치 | error — 대상 경로와 `kang bless` 인자 형식을 출력. 무엇이 바뀌었는지는 `git diff`가 보여준다 |
| import에 `rev` 핀이 없음 (세 종류 모두) | error — `kang bless` 가 삽입한다 (4.8) |
| 서로 다른 파일이 같은 이름의 심볼을 선언 (iknow 없음) | error — 관련된 모든 파일 경로를 로그에 명시 |
| `iknow` 가 관련 파일 전체를 상호 명시하지 않음 | error — 누락된 파일 경로를 로그에 명시 |
| `iknow` 대상 파일이나 심볼이 존재하지 않음 | error |
| import 그래프에 순환 존재 | error — 순환 체인 전체를 출력하고 공통 개념 추출을 안내 |

`iknow`는 keyword / topic / exception 세 심볼 모두에 똑같이 적용된다. N개 파일이 같은 이름을 선언하면, N개 파일 모두가 나머지 전부를 `iknow`로 명시해야 한다. **`iknow` 는 import 간선을 만들지 않으므로, 상호 명시가 순환 error 를 만들지 않는다** (4.4).

이름 충돌은 **전체 경로 기준**으로 판단한다. `결제`.`상태` 와 `구독`.`상태` 는 다른 이름이다 (4.3).

### 5.1.1 진단 출력

컴파일이 실패하면, 에이전트가 볼 수 있는 것은 **진단뿐**이다. 에이전트가 진단을 보고 스스로 고치지 못하면, 도구는 쓸모가 없다. 그래서 출력 형식을 여기서 정해 둔다.

진단에는 세 요소가 항상 있다.

- **관련 위치 전부.** 한 곳만 보여 주면, 에이전트가 나머지를 찾아 헤맨다.
- **왜 문제인지.** 규칙을 모르는 에이전트도 판단할 수 있어야 한다. 이 내용은 머리글 한 줄에 담는다.
- **그대로 적용할 수 있는 `fix`.** 셸 명령이면 인용 부호까지 포함한다.

**요소마다 출력 자리가 하나다.** 출력 자리는 아래 표의 세 가지다. 이 세 자리 밖에는 다른 문단을 두지 않는다.

| 자리 | 요소 | 필드 |
|---|---|---|
| `error[<코드>]: ` 로 시작하는 머리글 한 줄 | 왜 문제인지 + 어떻게 고치는지의 조건 | `message` |
| 두 칸 들여쓴 `<문서>.kang:<줄>` 줄들 | 관련 위치 전부 | `locations` |
| `  fix:` 아래의 `[edit]`, `[shell]` 항목들 | 그대로 적용 가능한 `fix` | `fixes` |

**설명을 담는 별도 문단(`detail`)은 두지 않는다.** 요소가 셋이고 자리가 셋이면, 파싱하는 쪽은 "머리글 한 줄 = 설명 전부" 라는 규칙 하나만 배우면 된다. 설명을 머리글과 문단으로 나누면, 읽는 쪽이 둘을 이어 붙여야 한다. 그러면 이어 붙이는 규칙이 새로 필요하다. 그래서 머리글은 문장이 여러 개여도 한 줄이다.

**미해결 심볼**

```
error[K001]: 선언되지 않은 심볼 — `승격`. 이 문서는 이 이름을 선언하지도 import 하지도 않았습니다. 같은 이름을 선언한 문서가 1 개 있습니다: docs/core/baseline. 같은 개념이라면 import 하고, 다른 개념이라면 이 문서에서 선언한 뒤 양쪽에 iknow 를 붙이세요.

  docs/policy/regression.kang:7   본문에서 참조했습니다

  fix:
    [edit]  docs/policy/regression.kang
            import 블록에 다음 줄을 추가하세요: import `docs`/`core`/`baseline`.`승격`
    [shell] kang bless 'docs/policy/regression' --import 'docs/core/baseline.승격'
```

**`iknow` 누락**

```
error[K012]: 같은 이름의 심볼이 여러 파일에서 선언됨 — `epoch`. iknow 상호 명시가 완전하지 않습니다. 다른 뜻이라면 각 선언에 iknow 를 붙여 상호 명시하고, 같은 뜻이라면 한쪽을 지우고 다른 쪽을 import 하세요.

  docs/core/baseline.kang:6   여기서 선언했습니다 — keyword `epoch`
  docs/core/draft.kang:5      여기서도 선언했습니다 — keyword `epoch`

  fix:
    [edit]  docs/core/baseline.kang
            keyword `epoch` 선언 줄 끝에 다음을 추가하세요: // iknow `docs`/`core`/`draft`.`epoch`
    [edit]  docs/core/draft.kang
            keyword `epoch` 선언 줄 끝에 다음을 추가하세요: // iknow `docs`/`core`/`baseline`.`epoch`
```

**`fix` 의 머리글은 언제나 `fix:` 다.** 고치는 방법이 조건에 따라 달라지면, 그 조건은 `message` 에 적는다. `fix` 에는 고치는 방법 하나를 순서대로 담는다. `fix:` 머리글에 조건을 붙이면, 파싱하는 쪽이 머리글 문법을 하나 더 배워야 한다. 그런데 그 조건은 이미 진단의 첫 머리글 줄에 있다.

`fix` 는 **순서가 있는 목록**이다. 각 항목에는 종류가 있다.

| 종류 | 문법 | 예 |
|---|---|---|
| `[edit]` | **문서 문법.** 백틱을 쓴다 (4.2) | ``// iknow `docs`/`B`.`금액` `` |
| `[shell]` | **CLI 문법.** 백틱을 쓰지 않고 인용한다 (6.0) | `kang bless docs/B --import 'docs/A.결제'` |

두 문법을 섞으면 안 된다. `[edit]` 를 CLI 문법으로 쓰면, 넣은 줄이 4.2 를 어긴다. `[shell]` 을 문서 문법으로 쓰면, 셸이 백틱을 명령 치환으로 읽어 실행이 실패한다.

**`fix` 는 줄 번호로 위치를 지정하지 않는다.** 에이전트가 첫 `fix` 를 적용하면 줄이 밀리고, 두 번째 `fix` 의 줄 번호가 틀린다. 무엇을 고칠지는 심볼과 선언으로 지정한다 ([ADR-0003](../../docs/adr/0003-symbolic-addressing-not-line-numbers.kang)). 줄 번호는 `location` 에만 나온다. 그 줄 번호는 "여기를 보라" 는 표시일 뿐이고, 다음 명령의 인자가 아니다.

**`rev` 불일치**

```
error[K021]: rev 핀이 대상의 현재 내용과 다릅니다 — `docs`/`core`/`baseline`.`승격`. 핀은 참조 시점의 내용을 가리킵니다 (스펙 4.8). 무엇이 달라졌는지는 프로젝트 루트에서 git diff 'docs/core/baseline.kang' 로 확인하고, 이 문서가 지금의 대상에도 여전히 맞는지 확인한 뒤 핀을 갱신하세요.

  docs/billing/invoice.kang:5   여기서 import 했습니다 — 핀 000000, 현재 046f50

  fix:
    [shell] kang bless 'docs/billing/invoice' --import 'docs/core/baseline.승격'
```

나머지 규칙도 같은 형식을 따른다. `code` 는 규칙마다 고정이다. 에이전트가 코드 값으로 분기할 수 있어야 하기 때문이다.

#### 문체

**한 실행에 두 문체가 섞이면 기계가 규칙을 하나로 배울 수 없다.** 자리마다 문체가 하나다.

**마침표는 문장 뒤에만 온다.** 값 뒤에는 오지 않는다. 경로, 심볼 이름, 명령처럼 복사해
쓰는 값 뒤에 마침표가 오면, 그 마침표가 값의 일부로 읽힌다. `.` 은 keyword 계층 구분자이고(4.3),
셸은 마침표를 인자에 넣는다. 자리별 문체는 이 한 규칙에서 나온다.

- **`message` 는 완전문이며 마침표로 끝난다.** 값으로 끝나는 문장만 예외다. 그 예외는 읽지 못한
  파일의 경로(`K051`)와, 채워 넣을 값(placeholder)이 있어 `[shell]` 로 출력할 수 없는 변환 명령(`K051` 의
  `iconv`)이다.
- **`note` 는 위치 표시이며 마침표로 끝나지 않는다.** 표시는 문장이 아니다. 설명을
  덧붙일 때는 줄표(`—`) 뒤에 쓴다. 그 설명이 완전문이어도 끝에 마침표를 두지 않는다.
- **`fix` 의 `action` 은 마침표로 끝나지 않는다.** `[shell]` 은 명령만 담는다(6.0).
  `[edit]` 는 지시문이다. 그래서 둘 다 문장으로 닫지 않는다.
- **스펙 절 번호 인용은 `message` 에만 둔다.** 규칙을 모르는 에이전트가 근거를 찾을
  곳은 한 곳이면 된다. `note` 는 위치를 가리키는 자리다. `note` 에는 절 번호를 인용하지 않는다.

#### `fix` 의 두 성질

**`fix` 는 두 가지로 나뉜다. 적용하면 해소되는 것과, 확인만 하는 것이다.**

- **적용하면 해소되는 `fix`.** 그대로 실행하거나 편집하면 그 진단이 사라진다. 이 종류가 기본이다.
  출력할 수 있으면 이 종류를 출력한다. 조건에 따라 나뉘는 여러 항목도 이 종류다. 각 항목은
  적용하면 해소되고, 어느 경우인지는 `message` 의 조건이 알려 준다.
- **확인만 하는 `fix`.** 실행해도 진단이 사라지지 않는다. 대신 다음에 무엇을 할지 판단할 값을
  준다. 이 종류는 두 경우에만 쓴다. 원인이 문서 밖에 있을 때(권한, 인코딩), 그리고 다음 명령의
  인자를 컴파일러가 알 수 없을 때다. `K051` 의 `ls -l`, `file -I` 가 이 종류다. 확인한 값으로
  무엇을 할지는 `message` 가 알려 준다.

확인만 하는 `fix` 만 출력할 수 있다면, 그 진단은 **문서의 잘못이 아니다.** 종료 코드도
6절의 환경 오류 코드로 나온다. 반대 방향은 맞지 않는다. `K050` 은 환경 오류이지만,
적용하면 해소되는 `fix` 인 `git init` 을 갖는다.

### 5.2 exception 상태 기계

| exception 상태 | cover 있음 | cover 없음 |
|---|---|---|
| 일반 | 통과 | **error** — 이 예외를 커버하는 정책이 없음 |
| `pending` | **error** — 미결정이라 선언했으나 커버가 존재함 | **warn** — 통과 |

한 exception 을 가리키는 `cover` **선언**이 둘 이상이면 error다. 예외 하나에 정책 하나만 허용한다.

**세는 것은 선언이고, topic 이 아니다.** 같은 topic 이 같은 예외를 두 번 cover 하는 것도 중복이다. 이때 "둘 이상의 topic 이 커버한다" 라고 말하면 진단이 틀린 말을 하게 된다. 남는 중복 선언은 뜻을 바꾸지 않으므로, 조용히 통과시킬 수도 있다. 하지만 그러면 컴파일러가 보고도 넘긴 쓸모없는 선언이 지워지지 않고 남는다. 고치는 방법은 두 경우 모두 같다. 실제로 그 예외를 다루는 `cover` 하나만 남긴다.

### 5.3 순환 검출의 단위

순환 검출은 **파일 단위**로 한다 (5.1). 파일 그래프가 DAG 이면 topic 그래프도 DAG 다. topic 간선 T→U 가 있으면 반드시 file(T)→file(U) 도 있으므로, 파일 단위로 금지하는 쪽이 더 강하다.

v2 의 참조 전파는 이 DAG 보장을 전제로 한다(`V0003` 2절). v1 에는 전파 결과를 쓰는 곳이 없다. 그래서 v1 은 그래프 값을 남기지 않고 순환만 검출한다.

## 6. CLI

```
kang init                               에이전트 진입점과 첫 문서 생성
kang build                              컴파일 및 검증
kang bless    <문서> --import <심볼>    rev 핀 갱신·삽입
kang list     [경로]                    문서 목록과 description
kang keywords [경로]                    키워드 목록
kang refs     <키워드>                  키워드를 참조하는 topic
kang show     <문서|토픽>               문서/토픽 조회 (YAML)
kang index    <경로>                    심볼 인덱스 생성 (탭 구분)
kang types    <경로>                    TypeScript 타입 생성 (topic)
kang inspect                            코드 대조 (v2)
```

`kang index` 와 `kang types` 는 코드 연동(7절)에 쓰는 파일을 생성하는 명령이다. 이 두 명령은 **`build` 와 따로 둔다.** `build` 는 파일을 쓰지 않기 때문이다. 두 명령은 error 가 하나라도 있으면, 아무것도 쓰지 않고 종료 코드 1 로 끝난다. 환경 오류이면 종료 코드 2 로 끝난다 (아래 표). 깨진 프로젝트에서 만든 파일을 다른 프로젝트가 읽으면, 그 프로젝트는 틀린 내용을 기준으로 검증하게 된다. 그래서 5절이 모든 CLI 명령에 요구하는 것과 같은 규칙을 쓴다. 통과하지 못한 문서는 어떤 명령으로도 출력하지 않는다. 형식은 `V0003-kang-v2-code-integration.md` §5 가 정한다.

`kang inspect` 는 v2 기능이다. v1 바이너리에서 호출하면, kang 은 "v2 기능이며 아직 구현되지 않았다" 를 명시하고 종료 코드 3 으로 끝난다. 없는 명령처럼 보이면, 에이전트가 철자가 틀렸다고 생각하고 다시 시도하기 때문이다.

**종료 코드**

| 코드 | 의미 |
|---|---|
| 0 | 성공 |
| 1 | 컴파일 error 존재 |
| 2 | 사용법 오류 (알 수 없는 명령, 인자 부족) + 환경 오류 (git 저장소 아님, 문서를 읽지 못함) |
| 3 | v2 기능 호출 |

에이전트는 종료 코드로 분기한다. 1과 2를 구분해야 "문서를 고쳐야 한다" 와 "명령을 잘못 썼거나 환경이 다르다" 를 나눌 수 있다.

**환경 오류인지는 원인이 문서 밖에 있는지로 정한다.** `K050`(git 저장소 아님)과 `K051`(권한
없음, UTF-8 아님)이 환경 오류이고, 둘 다 종료 코드 2 다. `K051` 에 종료 코드 1 을 주면, 에이전트가
열지도 못한 파일에서 고칠 문법을 찾는다. 그 진단의 `fix` 는 `ls -l`, `file -I` 이고,
"문서를 고쳐라" 라고 말하지 않는다 (5.1.1 의 확인만 하는 `fix`).

**`K051` 은 다른 error 와 함께 나와도 종료 코드 2 다.** 읽지 못한 파일이 있으면, 그 컴파일은
처음부터 문서 전체를 보지 못한 것이다. 그래서 남은 문서 오류를 고치기 전에 환경을 먼저 고쳐야
한다. 환경을 고친 뒤 다시 실행하면, 남은 오류가 종료 코드 1 로 나온다.

**사용법 오류에는 `--help` 를 함께 출력한다. 환경 오류에는 출력하지 않는다.** git 저장소가 아닌 것은 명령을 잘못 쓴 것이 아니다. 여기서 help 를 보여 주면, 에이전트가 철자가 틀렸다고 생각하고 다시 시도한다. 환경 오류에서는 `git init` 지시만 출력한다.

예외가 어디서 cover 되는지 보는 별도 명령은 두지 않는다. `kang show` 가 예외를 정의한 파일을 보여 줄 때 `coveredBy` 로 이미 출력한다.

### 6.0 CLI 인자 문법

**인자에는 백틱을 쓰지 않는다.** 셸에서 백틱은 명령 치환이고, 비대화형 호출에서도 명령 치환이 일어난다. LLM 에이전트는 kang 을 바로 이 비대화형 방식으로 호출한다. 그래서 백틱을 쓰면, 오류 메시지 없이 잘못 동작한다.

```
kang refs docs/A.결제
kang show 'docs/A#결제의 방법'
kang bless docs/B --import 'docs/A.결제 수단'
```

- 문서 본문의 백틱은 그대로 둔다 (4.2). CLI 인자는 별개 문법이며, `/`, `.`, `#`, `!` 만으로 파싱한다.
- 공백이 있는 이름은 셸 인용이 필요하다. 이것은 셸의 일반 규칙이다.
- **`kang build` 의 `fix` 문자열은 인용을 붙여 출력한다.** 에이전트가 복사해 그대로 실행할 수 있어야 한다. 인용이 필요한지 에이전트가 스스로 판단하게 두면 틀린다.
- **`fix` 의 `[shell]` 항목은 명령만 담는다.** 앞에 설명을 붙이면, 출력된 줄을 그대로 실행할 수 없다. 셸이 첫 단어를 명령으로 찾기 때문이다. 왜 그 명령을 실행하는지는 진단의 머리글 줄과 `location` 의 note 가 알려 준다 (5.1.1).

#### 주소 분할 규칙

**주소는 마지막 `/` 에서 나눈다.** 그 앞은 전부 디렉토리 경로다. 그 뒤는 문서 이름과 심볼 이름이다. 마지막 조각 안에서는 keyword `.`, topic `#`, exception `!` 중 가장 먼저 나오는 것이 구분자다.

```
v1.2/a#b/pay.결제        → 디렉토리 v1.2/a#b , 문서 pay , keyword 결제
docs/A#결제의 방법        → 디렉토리 docs , 문서 A , topic 결제의 방법
```

이 순서 덕분에 디렉토리 이름 안의 구분자는 문제가 되지 않는다. **전체 문자열에서 첫 `#`, `!` 를 먼저 찾는 규칙은 쓰지 않는다.** 그 규칙은 `v1.2/a#b/pay.결제` 처럼 디렉토리에 구분자가 있는 합법 경로를 깨뜨린다.

**첫 구분자 뒤는 전부 이름이다.** 마지막 `/` 에서 문서와 심볼의 경계가 이미 정해진다. 그래서 마지막 조각에서 첫 구분자를 찾은 뒤에는 더 나누지 않는다. 따라서 이름 안의 `.`, `#`, `!` 는 이름의 일부로 읽힌다.

```
docs/B.결제수단.카드           → 문서 B , keyword 결제수단.카드 (4.3 의 계층 이름)
docs/A#결제 v1.2 개요          → 문서 A , topic "결제 v1.2 개요"
docs/A!무료! 상품              → 문서 A , exception "무료! 상품"
```

**topic 과 exception 이름의 `.`, `#`, `!` 는 제약이 아니다.** 첫 구분자 뒤에 오므로 그대로 이름이 된다.

이름에서 금지하는 것은 두 가지뿐이다. **CLI 로 주소를 지정할 수 없는 이름은, 이름을 고친다.** 근거는 topic 헤딩의 백틱을 막는 것(`K105`)과 같다. 묘비를 남기지 않는 것과도 같은 방향이다.

1. **문서 파일 이름에 `.`, `#`, `!` 금지.** `docs/a.b` 라는 문서가 있으면, `docs/a.b.결제` 는 "문서 `a` 의 keyword `b.결제`" 로도, "문서 `a.b` 의 keyword `결제`" 로도 읽힌다. 컴파일러가 문서 목록을 뒤져 가장 길게 일치하는 것을 고를 수도 있다. 하지만 그 방법은 "구분자만으로 파싱한다" 는 이 절의 규칙을 어긴다. 또 경로 오타가 더 흔한데, 그 오타에 나와야 할 맞는 진단도 틀어진다. 이런 이름도 빌드를 막는다. `bless`, `refs` 가 이 이름을 가리킬 수 없으므로, import 하는 순간 build 가 영구히 error 상태에 머문다. `#` 이 들어간 이름은 `show` 도 열지 못한다. (`show` 는 `#` 로만 나누므로, `.` 이나 `!` 가 들어간 이름은 `show` 는 통과하지만 `refs`, `bless` 가 막힌다.)
2. **심볼 이름에 `/` 금지.** 마지막 `/` 에서 먼저 나누는 규칙이 이름 안을 자른다. `## 환불/취소` 는 컴파일은 통과한다. 하지만 그 topic 을 import 한 문서에는 어떤 명령으로도 핀을 붙일 수 없어서, 프로젝트가 영구히 error 에 머문다. 이름에 들어가는 `/` 가 `//` 뿐인 경우도 함께 막힌다. 헤딩 이름의 `// 메모` 처럼 modifier 단어가 아닌 `//` 는 이름의 일부가 되므로, 그 헤딩도 거부된다. `//` 를 쓰는 일반 문장은 이름이 아닌 곳(한 줄 정의, 본문)에 둔다.

- **심볼 이름의 `/`** 는 `K105`(topic 헤딩에 백틱)와 같은 종류의 검사다. 이름을 읽는 곳에서 같은 근거로 거부한다. 문서 파일 이름 문제와 둘 다 빌드를 막으므로 함께 해결한다. 코드는 `K115` 를 할당한다.
  - **선언만이 아니라 참조도 거부한다.** 선언만 막으면, 어느 문서도 그 이름을 선언할 수 없다. 그러면 `K001`(미선언 심볼)이 언제나 "이 문서에서 선언하세요" 를 수정 안내로 준다. 그 안내를 그대로 적용하면, 선언한 위치에서 다시 진단이 난다. 그러면 5.1.1 이 요구하는 "그대로 적용 가능한 `fix`" 가 아니게 된다. 4.2 가 "본문과 선언부의 모든 백틱은 심볼 참조" 라고 정했으므로, 참조의 백틱도 심볼 이름이다.
- **문서 파일 이름의 `.`, `#`, `!`** 는 문서를 읽어 들이는 단계에서 검사해야 하므로 새 코드가 필요하다. `K113` 을 할당한다 (`K100`-`K199` 문법 코드 범위의 다음 빈 번호).

- **주소가 될 수 없는 이름 세 가지를 더 막는다.** `K113` 과 같은 단계에서 검사하고, 수정 안내도 같다(`[edit]`, 이름을 고친다). 코드 번호만 다르다. 세 가지 모두 직접 실행해 재현한 뒤 해결했다.
  - **`K116`** — 경로 조각의 제어 문자. 주소는 `kang index` 가 출력하는 TSV 의 마지막 필드다. 인덱스를 출력하는 모듈은 "이름에 줄바꿈은 들어갈 수 없다" 를 형식이 안전한 근거로 쓴다. 하지만 이 근거는 *심볼 이름*에만 맞다. 주소는 문서 경로도 함께 담는다. 그래서 `docs/evil\ntopic deadbe forged` 같은 디렉토리 하나로, 인덱스에 필드 세 개를 갖춘 가짜 줄을 넣을 수 있다. 매크로는 그 줄을 진짜 핀으로 읽는다.
  - **`K117`** — 경로가 UTF-8 이 아님. `문서경로` 가 조각을 `to_string_lossy` 로 만든다. 그래서 서로 다른 잘못된 바이트열 두 개가 같은 `\u{fffd}` 로 바뀌고, 한 문서가 다른 문서를 조용히 덮어쓴다. 이 문제는 내용이 UTF-8 이 아닌 `K051` 과 다르다. `K117` 은 이름이 문제이고, 내용은 정상일 수 있다.
  - **`K118`** — 첫 경로 조각이 `-` 로 시작. CLI 인자가 `-` 로 시작하면 플래그로 읽힌다. 그래서 `show`, `refs`, `bless` 가 그 인자를 받지 못한다. 이전에는 그런 문서가 `build` 를 통과하고 `list` 에도 나왔지만, 조회만 되지 않았다. 6절의 인자 파서는 이 경우의 수정 안내를 이미 "이름을 고친다" 로 정해 두었다. 하지만 그런 이름이 있다는 것을 알려 주는 곳이 없었다. 하위 조각의 `-` 는 합법이다. 주소 전체가 `-` 로 시작하지만 않으면 된다.

**keyword 이름의 한 조각 안에 있는 `.` 은 금지하지 않는다.** 이전 판은 이것을 금지했다. 근거는 "`.` 은 4.3 의 계층 구분자이므로 조각 안의 `.` 과 조각 사이의 `.` 을 구별할 수단이 없다" 였다. 그 관찰은 맞다. 하지만 결과가 해롭지 않다. 스코프의 키는 조각을 `.` 으로 이은 전체 이름이다. 그래서 두 가지 읽기가 같은 키가 된다. `` keyword `버전 1.2` `` 는 `build`, `keywords`, `refs`, `show`, `import`, `bless` 의 전체 과정을 모두 통과한다. 두 읽기가 서로 다른 선언을 가리키는 경우도 있다(`` `결제`.`카드` `` 와 `` `결제.카드` `` 를 한 스코프에 함께 묶는 경우). 이 경우는 이미 `K052`(한 이름이 두 번 묶임)가 수정 안내와 함께 거부한다. 반대로 금지하면, `Node.js`, `버전 1.2` 처럼 지금 통과하는 자연스러운 이름을 거부하게 된다. 금지 범위를 넓히는 쪽으로 틀리는 비용이 더 크다.

남는 문제는 하나뿐이다. 진단이 그 이름을 **정규 표기로 다시 쓸 때** 조각이 달라진다 (`` `버전 1.2` `` → `` `버전 1`.`2` ``). 가리키는 심볼은 같고, `fix` 의 CLI 주소도 정확하다. 그래서 수정 안내는 그대로 동작한다.

### 6.1 `kang init` — 에이전트 진입점

kang 의 주 사용자는 **다른 프로젝트에서 일하는 LLM 에이전트**다. 그런데 "LLM 은 원본을 보지 않는다" 는 원칙은 강제할 수 없다. 에이전트는 `.kang` 파일을 그냥 읽을 수 있기 때문이다.

그래서 이 원칙은 **에이전트가 kang 이 있다는 것과 사용법을 알 때만** 지켜진다. 저장소에 `.kang` 파일만 있으면, 에이전트는 그 파일이 무엇인지 모르고 `cat` 으로 읽는다. 그리고 `cat` 으로 읽은 `.kang` 은 import 간접 참조 때문에 마크다운보다 읽기 어렵다. 도구를 도입했는데 오히려 더 나빠진다.

`kang init` 이 이 문제를 해결한다. `kang init` 은 네 파일을 쓴다.

| 파일 | 역할 |
|---|---|
| `.claude/skills/kang/SKILL.md` | Claude 용 스킬. 케이스별 기대 동작 |
| `AGENTS.md` | Codex 용. **내용을 복제하지 않고 `SKILL.md` 를 가리킨다** |
| `CLAUDE.md` | 한 줄 진입점 — "이 프로젝트의 문서는 kang 으로 관리한다. kang 스킬을 사용한다" |
| 첫 `.kang` 문서 | frontmatter 가 채워진 템플릿 |

**저장소에 커밋되는 프로젝트 스코프 파일로 만든다.** 전역 스킬 설치를 요구하면 설치 단계가 늘고, clone 하는 사람마다 상태가 달라진다. 파일이 저장소에 있으면 clone 하는 순간 함께 받는다.

**스킬 내용은 `SKILL.md` 한 곳에만 있다.** `AGENTS.md` 와 `CLAUDE.md` 는 `SKILL.md` 를 가리키기만 한다. 같은 내용을 두 파일에 복사하면, kang 이 막으려는 바로 그 SoT 분열이 kang 자신의 도구에서 생긴다.

기존 `CLAUDE.md`, `AGENTS.md` 는 **덮어쓰지 않는다.** 섹션만 덧붙인다. 이미 kang 섹션이 있으면 건너뛴다.

**`SKILL.md` 는 kang 이 관리한다.** 내용이 바이너리의 스킬과 다르면 `kang init` 이 통째로 바꾼다. 같으면 건너뛴다. 그래야 새 바이너리를 받은 사용자가 `kang init` 한 번으로 새 사용법을 받는다.

**`kang init` 은 git 저장소를 요구하지 않는다.** 프로젝트 루트가 git 루트라는 규칙(3절)은 문서를 해석하는 명령에만 적용된다. `init` 은 방금 만든 디렉토리에서 실행하는 첫 명령이다. 그래서 git 저장소가 아니면, 현재 디렉토리를 루트로 삼아 파일을 만들고 `git init` 을 안내하는 문구를 함께 출력한다. 여기서 종료 코드 2 로 실패하면, 사용자는 T0 에서 바로 막힌다.

#### 스킬 내용

케이스별로 기대 동작을 적는다.

- **정책을 조회할 때** — `kang keywords` 로 개념 목록을 보고, `kang refs` 로 범위를 좁힌 뒤, `kang show` 로 읽는다. `.kang` 파일을 직접 열지 않는다. `show` 가 상위 정책을 전부 평탄화해 주므로 링크를 따라갈 필요가 없다.
- **정책을 쓸 때** — 먼저 `kang show` 로 관련 정책을 읽는다. 읽은 내용을 자기 문장으로 다시 쓰지 않고, `import` 로 참조한다. 서술을 복사하면 SoT 가 나뉜다 ([ADR-0002](../../docs/adr/0002-flatten-on-read-import-on-write.kang)).
- **컴파일이 실패했을 때** — 진단의 `fix` 를 그대로 적용한다. 셸 명령은 인용까지 포함해 출력되므로, 복사해 실행하면 된다.
- **개념 이름을 바꿀 때** — 그 개념을 참조하던 모든 문서가 깨진다. 전부 고친 뒤 각각 `kang bless` 한다. 묘비를 남기지 않는다 ([ADR-0001](../../docs/adr/0001-no-tombstones-for-retired-terms.kang)).
- **코드를 고칠 때** (v2) — 언어별 애노테이션 가이드. 코드가 어떤 정책을 구현하는지 표시하고 rev 핀을 맞춘다.

### 6.2 `kang bless`

rev 핀을 갱신하거나 삽입하는 유일한 명령이다.

```
kang bless <문서> --import <심볼>
```

`kang bless` 는 지정한 참조를 검토했다고 선언한다. 핀이 있으면 갱신하고, 없으면 삽입한다 (4.8).

- **주소는 심볼이다. 줄 번호를 쓰지 않는다.** 정상 워크플로가 "문서를 고친 뒤 bless" 이므로 줄이 밀린다. 밀린 줄 번호로 갱신하면 엉뚱한 핀을 조용히 바꾼다. 근거는 [ADR-0003](../../docs/adr/0003-symbolic-addressing-not-line-numbers.kang).
- 한 파일 안에서 같은 심볼을 두 번 import 하면 이미 error 다. 그래서 심볼 주소는 하나로 정해진다.
- **변경의 성격을 판단하는 옵션을 두지 않는다.** "이 변경은 사소하다" 는 범주 판단이다. 이런 범주 판단이 바로 kang 이 없애려는 LLM 판단이다. `bless` 가 주장하는 것은 범주가 아니라 "검토했다" 는 사실뿐이다.
- **한꺼번에 해제하는 수단이 없다.** 대상을 고치는 비용이 영향 범위에 비례하는 것은 의도한 설계다. 50곳이 참조하는 개념을 바꾸면 50곳을 확인해야 한다.
- 사소한 서식 변경은 4.8 의 정규화 규칙이 흡수한다. 그래서 핀이 깨지지 않는다.
- 의미가 바뀐 변경에는 별도 선언이 필요 없다. **아무것도 하지 않는 것이 기본 상태**다. 참조하는 쪽은 각 문서를 실제로 고친 뒤 `bless` 로 해제한다.

### 6.3 목록 출력 형식

목록형 명령(`list`, `keywords`, `refs`)은 **한 줄만 읽어도 뜻이 완결되는 형식** 하나만 출력한다. 경로는 항상 전체 경로이고, 계층을 줄여 쓰지 않는다. 이 규칙은 LLM 이 경로를 조립하다 틀리는 것을 막는다.

```
$ kang list docs
docs/A: {description}
docs/details/payment: {description}
docs/details/free-item: {description}
```

사람이 읽기 좋은 계층형 출력은 따로 제공하지 않는다. 이 도구의 독자는 LLM 이다. 출력 형식이 둘이면 코드 경로와 테스트도 둘이 된다.

### 6.4 `kang show`

kang 의 핵심 명령이다. 원본 파일을 그대로 보여 주지 않고, 관계 정보를 넣은 YAML 을 출력한다.

포함되는 정보:

- 이 파일이 정의한 키워드와, 그 키워드를 참조하는 topic 목록
- 이 파일이 참조하는 키워드와, 그 키워드를 정의한 파일
- 이 파일이 정의한 예외와, 그 예외를 cover 하는 내용
- 이 파일이 cover 하는 예외
- 각 topic 이 참조하는 키워드와 topic 을 **재귀적으로 포함**

출력 스키마:

```yaml
path: docs/B
keywords:                        # 이 파일이 정의한 키워드
  - name: 결제수단.카드
    path: docs/B
    description: 카드를 사용한 결제
    referencedBy:
      - docs/C#무료결제의 구성요소
referencingKeywords:             # 이 파일이 참조하는 키워드
  - name: 결제
    path: docs/A
    description: 사용자가 상품 대금을 지불하는 행위
exceptions:                      # 이 파일이 정의한 예외
  - name: 카드 수단 무료 결제
    pending: false
    coveredBy: docs/C#무료결제의 구성요소
    topic: |
      ## 무료결제의 구성요소

      무료결제는 `청구서` 와 `결제 내역` 레코드는 없고...
covers:                          # 이 파일이 커버하는 예외 (없으면 생략)
  - name: ...
    path: ...
    topic: |
      ...
topics:
  - name: 카드 결제
    uncoded: false
    topic: |
      ## 카드 결제

      `결제`를 하기 위한 수단 중 `결제수단`.`카드` 에 대한 설명이다.
    references:
      keywords:
        - name: 결제
          path: docs/A
          description: 사용자가 상품 대금을 지불하는 행위
          referencedBy:
            - docs/B#카드 결제
            - docs/C#무료결제의 구성요소
        - docs/A.결제수단          # 두 번째 도달은 포인터 한 줄로 줄어든다
      topics:
        - name: docs/A#결제의 구성 요소
          uncoded: false
          topic: |
            ## 결제의 구성 요소

            `결제`는 `청구서` 와 `결제 내역` 으로 이루어져 있다.
          references:
            ...
```

출력 규칙:

- 모든 경로는 계층 축약 없이 **전체 경로**로 표기한다.
- 여러 줄 본문은 literal scalar(`|`)를 쓴다. folded scalar(`>`)를 쓰면 줄바꿈이 합쳐져 마크다운 구조가 깨진다.
- **중복 제거** — 같은 topic 이나 키워드에 여러 경로로 도달하면, 처음 한 번만 펼친다. 그 뒤에는 경로 참조로 바꾼다.
- 출력 분량이나 토큰 규모를 표시하지 않는다. 깊이를 제한하는 옵션도 두지 않는다.
- **값이 빈 항목은 키까지 생략한다.** `keywords`, `referencingKeywords`, `exceptions`, `covers`, `topics`, `referencedBy`, `references` 는 담을 것이 있을 때만 나온다. 항상 있는 키는 `path` 하나다. 빈 목록으로 채우면, 조회 한 번의 절반이 정보 없는 `[]` 가 된다. `show` 의 독자는 그 토큰을 매번 읽는 LLM 이다. 출력을 읽는 코드가 치르는 비용은 `?? []` 한 번이다.

**포인터를 다시 조립하는 규칙은 심볼 종류마다 다르다.** 중복 제거된 두 번째 도달은 `docs/A.결제수단`, `docs/A#결제의 구성 요소` 같은 전체 주소 한 줄로 줄어든다. 출력을 사용하는 쪽은 그 문자열로, 먼저 펼쳐진 위치를 찾아야 한다. topic 은 펼쳐진 위치의 `name` 이 이미 전체 주소이므로 문자열이 그대로 일치한다. 하지만 키워드의 펼쳐진 위치는 `name`(계층 이름)과 `path`(owner 문서)로 나뉘어 있다. 그래서 `{path}.{name}` 으로 합쳐야 같은 문자열이 된다. 이 비대칭은 의도한 것이다. 키워드 항목의 `name` 을 전체 주소로 바꾸면, 위 스키마 예시의 `name: 결제수단.카드` 와 어긋난다. 그러면 한 개념의 이름을 두 표기로 부르게 된다. 그래서 키워드 항목은 `path` 를 반드시 함께 담는다. `path` 가 없으면 같은 이름을 선언한 다른 문서(4.4 `iknow` 로 합법이다)와 구별할 수 없다. 그러면 포인터가 가리킬 위치를 정할 수 없다.

#### 깊이 폭발 (v1 미구현, 모양만 확정)

import 폐포(import 를 따라가며 닿는 모든 대상)가 깊으면, `show` 한 번이 프로젝트 전체를 출력한다. 출력이 컨텍스트 한계를 넘으면 입력이 잘리고, 오류 없이 틀린 답이 나온다. v1 에서는 이 문제를 다루지 않는다. 데이터 없이 임계값을 고르면 추측일 뿐이다. 실제 숫자는 도그푸딩과 실제 코퍼스에서 얻는다.

나중에 구현할 때의 형태는 지금 정해 둔다.

- **읽을 때가 아니라 빌드할 때 막는다.** `show` 가 "너무 크니 줄여 읽어라" 라고 하면, 그 안내가 바로 LLM 에게 주는 선택권이다. 대신 어떤 topic 의 import 폐포가 N개를 넘으면, `kang build` 가 error 를 출력한다. LLM 은 선택지를 보지 못하고, 사람이 문서 구조를 고친다.
- **메시지는 "출력이 크다" 가 아니라 "이 문서가 참조하는 정책이 너무 많다" 다.** 컨텍스트 한계는 사용하는 쪽마다 다르다. 그래서 진단이 컨텍스트 한계에 의존하면 안 된다. 구조 문제로 말해야 다른 규칙들과 같은 수준에 놓인다.

즉 이 검사는 출력 제한이 아니라 **구조 린트**다. 한 정책이 상위 정책 10개에 의존한다면, 대개 그 정책이 너무 많은 일을 한다는 신호다.

$ kang refs docs/A.결제
docs/A#결제의 방식
docs/A#결제의 종류
docs/details/payment#결제의 방법
```

`kang inspect` 로 코드와 문서를 대조하는 설계는 **`V0003-kang-v2-code-integration.md`** 에 있다. v1 구현 대상이 아니므로 여기에 두지 않는다.

## 8. 비목표와 한계

- **kang 은 "옳음"을 검증하지 못한다.** 자연어이기 때문이다. kang 은 다음을 판단할 수 없다. 두 정책이 서로 모순되는지, `cover` 가 실제로 그 예외를 다루는지, 애노테이션이 붙은 코드가 정책대로 동작하는지. 마지막 것은 테스트가 맡는다.
- **대신 "재검토했음"은 100% 기계적으로 강제한다.** 실무에서 생기는 문제는 "누가 틀린 판단을 했다" 가 아니라 "아무도 다시 보지 않았다" 다. rev 핀이 이 문제를 결정론적으로 잡는다.
- 역할 분담은 다음과 같다.

| | 주체 | 방식 |
|---|---|---|
| 판단 | 사람 / LLM | 결과를 선언으로 고정한다 — `pending`, `iknow`, `uncoded`, `rev` 핀 |
| 검사 | 컴파일러 | 선언과 실제의 어긋남을 100% 기계적으로 검출한다 |
- **자연어 검색을 제공하지 않는다.** 임베딩이나 LLM 판단은 확률적이므로 믿을 수 없다. `kang keywords` 로 개념 목록을 보고 `kang refs` 로 좁히는 결정론적 탐색이 검색을 대신한다. 키워드가 곧 색인이다.
- **버전 관리를 하지 않는다.** 버전 관리는 git 이 맡는다. 언어에는 deprecated 를 표현하는 수단이 없다.

## 9. 미결정 사항

### 결정됨 (V0004)

- **언어별 애노테이션의 이름과 인자 형태.** Rust 는 `#[kang::topic("docs/A#…", rev = "a3f9c1")]` 이며, `keyword`, `covers` 도 같은 형태다. TypeScript 는 `kangTopic(topic, rev)` 이다. 생성된 `KangTopics` 의 `keyof` 제약과 리터럴 rev 로 `tsc` 가 검증한다. 매크로는 원본 아이템을 그대로 반환하므로 런타임 비용이 0이다.
- **심볼 인덱스 파일의 포맷.** `kang index <경로>` 가 한 줄에 `{종류}\t{rev}\t{주소}` 를 쓴다. 사용하는 쪽은 의존성 없이 `splitn(3, '\t')` 로 읽는다. 결정의 핵심은 길이가 변하는 주소를 마지막에 둔 것이다. 심볼 이름에 탭이 들어가는 것은 합법이다. 주소를 앞에 두면 그 줄의 필드가 넷이 되고, 사용하는 쪽이 오류 없이 잘못 읽는다.

### 남은 것

- **에러 메시지 포맷** — 5.1.1 이 요소, 문체, `fix` 의 두 성질을 정했다. 남은 것은 기계가 읽는 형식이다. 지금 사용하는 쪽은 종료 코드와 `[shell]`, `[edit]` 줄만 보고, `message` 를 나누어 읽지 않는다. `kang inspect`(v2)가 진단을 구조로 읽어야 할 때, JSON 출력 여부를 정한다.
- **중첩 프로젝트** — import 주소가 루트 기준이므로, 한 문서가 두 루트에서 동시에 유효할 수 없다. `examples/ts-consumer` 가 이 문제를 만났고, 문서를 그 안에서 완결되게 두어 피해 갔다. 이 결정은 3절의 "설정 파일을 두지 않는다" 와 함께 따져야 한다. 그래서 v1 에서는 정하지 않고 열어 두었다.

### 10.1 의존성 목록

크레이트마다 허용하는 외부 의존성을 여기에 나열한다. **목록에 없는 것은 쓰지 않는다.** 의존성을 늘려야 하면, 이 절을 고치고 근거를 남긴다. 제약의 범위를 다르게 해석하지 않는다. 워크스페이스 안의 크레이트끼리 쓰는 path 의존은 외부 의존성이 아니다. 그래서 이 목록에 나열하지 않는다. path 의존은 공급망도 빌드 시간도 늘리지 않는다. 첫 사례는 `kang` 이 `kang-macros` 에 의존해 자기 코드에 매크로를 붙이는 것이다(V0004 Task 6).

| 크레이트 | 허용 의존성 | 근거 |
|---|---|---|
| `kang` (CLI·컴파일러) | `sha2` | 표준 라이브러리에 SHA-256 이 없다. 인자 파싱과 YAML 출력은 직접 쓴다 — 플래그가 적고 YAML 스키마가 고정이다 |
| `kang-macros` (proc-macro) | `syn`, `quote`, `proc-macro2` | 속성 인자를 손으로 파싱하면 한글·공백·`#` 이 든 리터럴에서 취약해지고, 진단 품질이 떨어진다. proc-macro 는 Rust 가 별도 크레이트를 요구한다 |

proc-macro 크레이트를 따로 둔 것은 선택이 아니라 Rust 의 요구다. `proc-macro = true` 는 같은 크레이트의 바이너리, 라이브러리와 함께 있을 수 없다.

**컴파일러가 심볼 인덱스를 생성하고, 매크로가 그 인덱스를 읽는다.** 매크로는 컴파일러의 자료 구조에 의존하지 않는다. 그래서 두 크레이트의 의존성 목록이 서로 섞이지 않는다.
