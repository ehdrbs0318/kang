# V0003 — kang v2 코드 연동 설계

이 문서는 `kang inspect` 의 설계를 적는다. `kang inspect` 는 문서와 코드를 자동으로 비교한다. 이 문서는 **v2** 의 설계다. v1 의 설계는 `V0001-kang-language-design.md` 에 있다. 이 문서의 내용은 v1 에서 구현하지 않는다.

V0001 1절(배경)의 2번 문제(코드와 문서의 불일치)를 푸는 일의 절반을 이 문서가 맡는다. v1 은 문서 사이의 참조를 강제한다. v2 는 그 참조 검사를 코드까지 넓힌다.

---

## 1. `kang inspect`

`kang inspect` 는 코드에서 kang 심볼 참조를 모은다. 그리고 모은 참조를 문서와 비교한다.

검사 항목:

- 특정 keyword 를 참조하는 코드의 개수와 위치
- 특정 topic 을 참조하는 코드의 개수와 위치
- 특정 exception 을 참조하는 코드의 위치
- 특정 cover 를 구현하는 코드의 위치
- 죽은 정책 찾기

v1 바이너리에서 `kang inspect` 를 실행하면, "v2 기능이며 아직 구현되지 않았다" 를 알리고 종료 코드 3 으로 끝난다 (V0001 6절).

## 2. 참조 전파

코드가 어떤 topic 을 참조하면, 그 topic 이 import 하는 상위 topic 도 참조된 것으로 본다. 이 규칙은 재귀적으로 적용한다. import 그래프는 DAG 이므로 "상위" 의 뜻이 하나로 정해진다. 순환 때문에 잘못 판단하는 일도 없다.

**이 규칙을 쓰는 곳은 v2 에만 있다.** 참조 전파는 코드가 topic 을 참조할 때 정의된다. `kang show` 는 import 한 topic 을 재귀적으로 포함해서 출력한다. 이때 import 관계를 직접 따라가므로 전파가 필요 없다. v1 의 `resolve` 에는 참조 전파 함수가 없다.

## 3. 참조 표기 수단

주석보다 **언어에 내장된 선언 기능**(애노테이션)을 먼저 쓴다. 주석은 어느 코드에 붙은 것인지 애매하다. 애노테이션은 AST 노드에 구조적으로 붙는다. 그래서 리팩터링으로 코드가 바뀌어도 애노테이션이 코드와 함께 따라간다.

| 언어 | 수단 | 특징 |
|---|---|---|
| Rust | proc-macro 속성 | 컴파일 타임 실행, 런타임 비용 0, **검증까지 가능** |
| JVM | 애노테이션 (`RetentionPolicy.SOURCE`) | 런타임 비용 0, 클래스, 메서드, 필드 모두 적용 |
| TypeScript | 데코레이터 | **일반 함수에 적용 불가**, 런타임 비용 있음 |
| Python | 데코레이터 | 모듈 레벨 상수에 적용 불가, 런타임 비용 있음 |

TypeScript 데코레이터는 레거시(`experimentalDecorators`)와 표준(Stage 3) 모두 **클래스, 메서드, 접근자, 프로퍼티에만** 붙는다. 일반 함수 선언, 타입, 상수 export 에는 쓸 수 없다. Python 데코레이터도 모듈 레벨 상수에는 쓸 수 없다.

그래서 **주석 폴백**도 함께 지원한다. 주석 폴백은 애노테이션 대신 주석으로 참조를 적는 방법이다.

```
// kang: docs/A#결제의 방법        Rust, TS, Go, Java
#  kang: docs/A#결제의 방법        Python
```

`kang inspect` 는 두 형태를 모두 인식한다. 다만 **애노테이션을 쓸 수 있는 위치에 주석을 쓰면 warn** 을 출력한다. 이 경고는 kang 의 일관된 원칙을 따른다. 더 나은 방법이 있는데 쓰지 않으면, kang 은 계속 경고해서 불편하게 만든다.

## 4. 코드 참조도 rev 핀을 갖는다

코드의 정책 참조에도 V0001 4.7 의 rev 핀을 적용한다. 문서가 바뀌면, 그 문서를 참조하는 코드가 검사를 통과하지 못한다. 사람이 코드를 확인한 뒤에야 검사를 통과한다.

```rust
#[kang::topic("docs/A#결제의 방법", rev = "a3f9c1")]
pub fn process_payment() { }
```

```typescript
@kangTopic("docs/A#결제의 방법", "a3f9c1")
process() { }
```

```
// kang: docs/A#결제의 방법 rev a3f9c1
```

`kang inspect` 는 핀 불일치를 error 로 보고한다. 핀 불일치는 **`kang bless <문서> --import <kang 심볼>` 로 해제한다.** 코드 쪽 주소를 새로 만들지 않는다.

### 코드 심볼 이름은 CLI 주소에 담지 않는다

**결론: 담을 수 없고, 담을 필요도 없다.** 다음 사람이 매크로에 코드 이름을 넣으려고 하지 않도록, 그 근거를 여기에 적는다.

담을 수 없는 이유는 하나다. V0001 6.0 은 주소를 구분자만으로 파싱하고, `/`, `.`, `#`, `!` 를 예약한다. `crate::mod::fn` 의 `::`, 경로 조각의 `/`, 제네릭의 `<>` 는 이 문법과 바로 충돌한다. 6.0 은 이런 충돌의 수정 안내도 정해 두었다. "CLI 로 주소를 댈 수 없는 이름은 이름을 고친다"(`K105`, `K115`). 그런데 이 수정 안내는 **코드 심볼에는 쓸 수 없다.** 코드의 이름은 kang 이 정하지 않으므로, kang 이 이름을 고치라고 할 수 없다. 그래서 코드 이름을 주소에 담으려면 이스케이프 문법을 새로 만들어야 한다. 그러면 6.0 의 "구분자만으로 파싱한다" 규칙을 버려야 한다.

담을 필요가 없는 이유는 둘이다.

- **rev 핀은 kang 심볼의 성질이다.** 어느 코드 위치에서 참조하든 `docs/A#결제의 방법` 의 핀은 하나뿐이다. 그래서 해제 대상은 코드 위치가 아니라 kang 심볼이다. 같은 심볼을 가리키는 코드 위치가 여럿이면, 전부 갱신하는 것이 맞다. v1 의 `bless` 도 두 줄이 같은 심볼을 import 하면 이미 그렇게 한다. 코드 위치를 하나씩 지정하는 방법은 필요하지 않다.
- **위치 보고는 주소가 아니다.** 1절의 "코드의 개수와 위치" 는 `파일:줄` 형식으로 출력한다. [ADR-0003](../../docs/adr/0003-symbolic-addressing-not-line-numbers.kang)은 `location` 을 명시적 예외로 두었다. ADR-0003 에 따르면, 저장되는 값과 다음 명령의 인자가 되는 값만 심볼이어야 한다. "여기를 보라" 같은 표시는 그 순간에만 맞아도 된다. 코드 위치는 이 표시에 속한다.

그래서 애노테이션은 kang 심볼만 담는다 (4절의 예시도 이미 그렇다). 애노테이션이 붙은 위치가 코드 위치를 알려 주므로, 코드 이름을 적을 필요가 없다. 매크로가 생성하거나 검증할 문자열도 kang 주소 하나뿐이다. **`#[kang::topic("...")]` 의 인자는 CLI 주소와 문법이 같다. 그래서 V0001 6.0 의 두 금지 규칙이 그대로 이 문자열의 계약이 된다.**

## 5. 언어별 컴파일 타임 강제

`kang inspect --ci` 는 모든 언어에서 지키는 최소 보장이다. 그 위에 언어마다 더 일찍 알려 주는 검사를 더한다.

**Rust — proc-macro**

proc-macro 는 컴파일 타임에 실행된다. 그래서 표시만 하지 않고 검증도 한다.

- `kang build` 가 심볼 인덱스 파일을 생성한다.
- proc-macro 가 인덱스를 읽어, 심볼이 실제로 있는지와 rev 가 맞는지를 확인한다.
- 불일치는 **컴파일 에러**다. `kang inspect` 를 실행하기 전에 빌드에서 잡힌다.
- `build.rs` 의 `cargo:rerun-if-changed` 로 인덱스를 추적한다. 그래서 문서가 바뀌면 반드시 다시 빌드된다.
- 매크로는 원본 아이템을 그대로 반환한다. 그래서 런타임 비용은 0이다.

**TypeScript — 생성 타입**

데코레이터는 런타임에 실행된다. 그래서 데코레이터만으로는 `tsc` 가 검증하지 못한다. 대신 `kang build` 가 타입 파일을 생성해서, 검사를 타입 시스템으로 옮긴다.

```typescript
// .kang/generated.ts
export interface KangTopics {
  "docs/A#결제의 방법": "a3f9c1";
  "docs/B#카드 결제":   "b721e0";
}

export function kangTopic<K extends keyof KangTopics>(
  topic: K,
  rev: KangTopics[K],
): MethodDecorator {
  return () => {};
}
```

- 존재하지 않는 topic 이름은 `keyof` 제약 위반이므로 **타입 에러**다.
- 오래된 rev 는 리터럴 타입 불일치이므로 **타입 에러**다.
- 런타임 실행 없이 타입 체크만으로 잡힌다. IDE 에도 바로 표시된다.

**`declare` 대신 본문이 있는 함수로 생성한다.** `declare` 는 "이 이름이 어딘가에 있다" 는
선언일 뿐이고, 값을 만들지 않는다. 사용하는 프로젝트가 `generated.ts` 에서 `kangTopic` 을
import 하면, 타입 체크는 통과한다. 그러나 런타임에는 `undefined` 가 온다. 그래서 아무것도
하지 않는 데코레이터를 실제로 export 해서 이 문제를 막는다. 구현은
`examples/ts-consumer/.kang/generated.ts` 에 그대로 있다.

데코레이터를 붙일 수 없는 일반 함수는 주석 폴백을 쓴다. 이 경우는 `kang inspect --ci` 가 검사한다. ESLint 커스텀 룰을 만드는 방법도 있다. 이 방법을 쓰면 IDE 에 바로 표시되고, `--fix` 로 rev 를 갱신할 수 있다. 그러나 패키지가 늘어나므로, 필요해질 때 다시 판단한다.

## 6. 예외 미구현 검사

이 검사는 결정론적이다. 그래프 탐색만으로 결과를 정한다.

> 어떤 코드가 topic T를 참조하는데, T가 선언한 exception을 커버하는 정책을 구현한 코드가 어디에도 없으면 **warn**

지금까지는 예외 누락을 문서 레벨에서만 잡았다. 이 검사는 구현 레벨에서도 잡는다.

## 7. uncoded 상태 기계

| topic 상태 | 코드 참조 있음 | 코드 참조 없음 |
|---|---|---|
| 일반 | 통과 | **warn** — 죽은 정책 |
| `// uncoded` | **warn** — 코드가 있는데 uncoded로 선언됨 | 통과 |

`// uncoded` 문법은 v1 의 파서가 인식한다. 그러나 이 검사에는 코드가 필요하므로 `kang inspect` 가 한다.
